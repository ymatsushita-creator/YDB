マイグレーションに移す過程で加えた変更を、すべて理由付きで記録する。

原典は正典として `basic/` に置いたまま変更していない。

各項目の末尾に、その判断を固定しているテストを示す。

## A. 動かして見つかった不具合

### A-1. 日付境界がセッションのタイムゾーンに依存していた ★影響大

原典は日付への丸めを一貫して `x::date` で書いていた。`timestamptz::date` は
セッションの `TimeZone` 設定で結果が変わる。

実測（PostgreSQL 18.3 / PGlite）:

| セッション TZ | `'2025-04-01T08:00:00+09:00'::date` |
|---|---|
| Asia/Tokyo | 2025-04-01 |
| UTC | **2025-03-31** |
| America/New_York | **2025-03-31** |

JST 09:00 より前に起きたことがすべて前日に寄る。応募開始日の朝に届いた
応募は「応募開始前」に計上され、日次ファネルの初日が丸ごとずれる。
接続文字列を書き換えただけで過去の集計値が動く状態だった。

**対応**: `jst_date(timestamptz) -> date` を定義し、集計の日付境界はすべて
これを通す。タイムゾーンをリテラルで与えるため `IMMUTABLE` にでき、
式インデックスも張れる（`x::date` は `STABLE` 止まりで張れない）。

運用タイムゾーンを変えると過去の集計がすべて動く。Season の日付と同じ性質を
持つため、変更は必ずマイグレーションとして残すこと（原則4）。

→ `tests/02_time.test.ts`

### A-2. `void_reasons.counts_as_application` が誰にも読まれていなかった ★影響大

原典の `v_application_state` と `f_funnel_daily` は `voided_at IS NOT NULL` の
応募を無条件に除外していた。一方 `void_reasons` には

> `counts_as_application` は「この無効化に対応する代替の Application が
> 生まれるか」で決まる。名寄せ誤り → false（付け替え先で1件数える）、
> 取り下げ → true。

とある。代替が生まれない無効化（取り下げ）は、応募が起きた事実として
木に数えなければならない。無条件除外だと応募数が実態より少なく出て、
`counts_as_application` カラムは一度も参照されないまま残る。

**対応**: `v_countable_applications` を新設し、集計対象の定義を1箇所に置いた。

```sql
WHERE a.deleted_at IS NULL
  AND (a.voided_at IS NULL OR vr.counts_as_application)
```

`deleted_at`（個人情報削除）は性質が違うため無条件に除外を維持する。

なお原則7「事実の有無で判定し、理由で分岐しない」に反しないかを検討した。
この原則が禁じているのは理由テキストによる場当たりの分岐であり、
ここはマスタに宣言された真偽値を読んでいるだけなので抵触しない。

→ `tests/04_funnel.test.ts`「無効化された応募の扱い」

### A-3. 訂正チェーンに循環を作ると、記録が静かに消える

`v_effective_status_histories` は「誰にも訂正されていない行」を再帰の基底に
とる。h1 が h2 を訂正し h2 が h1 を訂正する状態を作ると、どちらも基底に
現れず、チェーンごと有効判定から脱落する。エラーにはならず、集計から
黙って消える。落ちるより悪い壊れ方をする。

循環検出トリガを書く前に、より根本的な性質に気づいた。
`corrects_history_id` は既存の行しか指せないため、INSERT だけで構成される
グラフの辺は必ず過去方向を向き、循環はそもそも作れない。循環が生まれるのは
UPDATE で後から辺を張り替えたときだけである。

**対応**: `status_histories` を追記専用にした（UPDATE / DELETE を拒否）。
これは原則5「訂正は打ち消しの追記で表現し、元の記録は残す」そのものであり、
循環検出は副産物として不要になる。個別の異常を潰すより、異常が生まれる
余地を閉じるほうを選んだ。

同じ理由で `season_revisions`（原則4）と `score_snapshots`（原則2）にも
適用した。

→ `tests/03_corrections.test.ts`「訂正チェーンの構造的な健全性」

### A-4. 集計窓に NULL を渡すと、もっともらしい0が返る

`f_funnel_daily(NULL)` は比較が NULL になり、林が黙って0人になる。
0人のファネルは異常だと気づけるが、「引数を渡し忘れた」とは気づけない。

**対応**: `require_positive()` で明示的に落とす。ガードは最外の `FROM` に
置き、Season が0件でも必ず評価されるようにした。

→ `tests/01_schema.test.ts`「集計関数の引数」

### A-5. `is_correction` とチェーンが食い違いうる

原典は「`is_correction = true` なら `corrects_history_id` が必要」の片側しか
縛っていなかった。`corrects_history_id` を持ちながら `is_correction = false`
の行が作れる。有効性判定は `corrects_history_id` しか見ないため、
食い違うとフラグのほうが嘘になる。

**対応**: 逆向きの CHECK を追加し、両者を同値にした。

→ `tests/03_corrections.test.ts`

### A-6. 名寄せ判定が (A,B) と (B,A) の二重登録を許していた

`UNIQUE (person_id, candidate_person_id)` は順序違いの重複を防がない。
「AとBは別人」と「BとAは同一人物」を同時に登録できてしまい、
同じ組を毎年候補に上げないという目的が崩れる。

**対応**: `CHECK (person_id < candidate_person_id)` で組を正規化した。
書き込み側は挿入前に2つの id をソートする必要がある。

→ `tests/05_constraints.test.ts`「名寄せ判定の一意性」

### A-7. アトリビューションが同時刻の接点で非決定的だった

`DISTINCT ON (person_id, season_id) ... ORDER BY occurred_at` は、同時刻の
接点が複数あると勝つ行が実行ごとに変わりうる。同じ質問に日によって
違う答えが返るダッシュボードは信用されない。

**対応**: `touchpoint_id` を第2ソートキーに足して決定的にした。

→ `tests/06_person_state.test.ts`「同時刻の接点があっても結果が揺れない」

### A-8. 集計の計算量が実用に耐えない ★影響大

原典の意味論は正しいが、そのままでは画面が出ない。原因は2つ。

具体的なミリ秒はここに書かない。手元にあるのは `src/seed/demo.ts` が作った
架空のデータで、そこから出た数字を「実測」として記録すると、追試できない値に
権威が付く。デモデータの規模を変えれば数字も変わる。残す価値があるのは、
データ量に依存しない計算量のほうである。

**(1) 相関副問い合わせの繰り返し評価。** `f_funnel_daily` が返す行は
（年度 × 選考期間の日数）。そのそれぞれが6本の相関副問い合わせを走らせ、
うち4本が `v_effective_status_histories`（訂正チェーンを解く再帰CTE）を
先頭から評価し直す。訂正の解決が「返す行数 × 4」回起きる。
選考期間を延ばすだけで線形に悪化する。
`v_application_state` も応募1件につき EXISTS を3本、同様に再帰を繰り返す。
`v_person_season_state` はそれを引くので巻き込まれる。

→ 訂正の解決は1回だけ。応募ごとに「いつ幹になったか / いつ落ちたか /
いつ辞退したか」を1行に畳み、日次の増分をウィンドウ関数で累積する。
EXISTS は `bool_or` 付きの集約に置き換えた。

**(2) 林の日ごとの重複排除。** (1) を潰したあとに残るのはこれ。
日ごとに `count(DISTINCT person_id)` を取り直しており、
日数 × 窓内の接点数だけ重複排除が走る。窓を広げても日数を増やしても効く。

→ 各 Person の「アクティブでいる期間」を区間として求め、重なる区間を
1本にまとめ、開始日に +1 / 終了翌日に -1 を立てて暦日で累積する。
区間に畳んでから数えるので、同じ人を二度数えることが構造的に起きない。

意味論を変えていないことは、素朴な実装を参照として残し、ランダムな
敵対的データ（二重訂正・両種の無効化・合格前の辞退・差し戻し・年度外の遷移・
削除済み Person・期間の重なる年度）で1行ずつ突き合わせて確認している。
→ `tests/07_funnel_equivalence.test.ts`、`tests/08_state_equivalence.test.ts`

ただし 07 の参照実装は **0002 の定義であって原典そのものではない**。
0002 は既に A-1・A-2・C-1 を反映済みだからで、07 が保証しているのは
「0004 ≡ 0002」である。「0002 ≡ 原典」のほうは A-1 / A-2 / C-1 の
各テストが個別に担保している。08 の参照実装は原典 `basic/` の EXISTS 版そのもの。

### A-9. `GREATEST()` は NULL を伝播しない

上記の書き直しで実際に踏んだ。PostgreSQL の `GREATEST` / `LEAST` は、
多くの関数と違い NULL 引数を**無視して**非 NULL の最大値を返す。

```sql
SELECT greatest(NULL::date, '2025-11-01'::date);  --> 2025-11-01（NULL ではない）
```

「まだ合格していない」を表す NULL を応募開始日に丸めるつもりで
`greatest(accepted_day, application_open_date)` と書いたところ、
NULL が消えて**全応募が年度初日に合格したこと**になった。

テストが即座に落ちたので実害はなかったが、性質そのものを
テストに残してある。→ `tests/07_funnel_equivalence.test.ts`

### A-10. 個人の「林」と、年度サマリの「林」が桁違いだった ★影響大

個人を1人引く画面を作ろうとして見つかった。同じ言葉が2つの違う定義を
指していた。

| 出どころ | 定義 |
|---|---|
| `v_person_season_state.current_level = 'identified_person'` | その年度に応募していない識別済みの人。**窓を持たない** |
| `f_funnel_daily.identified_person_cum`（林の KPI） | 基準日から遡って N 日以内に接点がある人 |

前者で「林」と表示された人が、後者に数えられているとは限らない。
デモデータの2027年度では前者が 2,576 人、後者が 661 人になる。
個人の画面が前者をそのまま「林」と出せば、①（誰がどんな状態か）の
答えが見る画面で変わる。CLAUDE.md 3節の「単位の違うものを同じ軸に
置かない」を、名前の側で破っていた形になる。

**対応**: 段（`current_level`）と接点の鮮度を、直交する2つの事実として
並べた（`f_person_season_state(active_window_days)`、0010）。
段は「その年度に到達した最高地点」、鮮度は「基準日時点で生きている接点が
あるか」で、そもそも別の軸である。木や幹になった人も接点を持てば林の窓に入る。

段ごとに数えて足しても年度サマリの林にはならないが、**段を問わず窓の
内側を数えれば一致する**。この一致がドリルダウンと年度サマリをつなぐ
唯一の約束なので、テストで固定した。画面（`/people`）にも両方を並べ、
一致していなければその場で分かるようにしてある。

`v_person_season_state` そのものは変えていない。資料2-3「林に期は存在
しない。存在するのは Person に対する期スコープの検索結果である」の
実装であり、窓を持ち込むと位置づけが崩れるうえ既存の集計に波及する。

基準日は「選考終了日と今日の早いほう」。終わった年度で今日を基準にすると
選考終了後に付いた接点で過去の林が動き、進行中の年度で選考終了日を
基準にするとまだ来ていない日の値を出すことになる。

→ `tests/12_drilldown.test.ts`「「林」と表示される人が、年度サマリの林に数えられているとは限らない」、
   12「段を問わず窓に入っている人の数は、ファネルの林と一致する」、
   12「基準日は選考終了日と今日の早いほう」、
   12「窓に 0 や NULL を渡すと落ちる」

### A-11. 年度を指定した検索が、外側の行ごとに集計関数を評価し直していた ★影響大

`/people` を開いたら 2.6 分かかった。A-8 と同じ構造の問題が、
今度は問い合わせの書き方の側で出た。

原因は `LEFT JOIN f_person_season_state($4) ps ON ps.person_id = p.id
AND ps.season_id = $2`。集合を返す関数を結合の内側に置くと、
プランナが入れ子ループを選んだときに **Person 1行ごとに関数全体を
評価し直す**。関数そのものは速く（単体で 0.2 秒弱）、遅いのは
呼ばれ方のほうだった。

実測の切り分け:

| 問い合わせ | 時間 |
|---|---|
| 年度を指定しない検索（関数を使わない） | 0.6 秒 |
| 年度を指定した検索 | **444 秒** |
| 氏名で絞り込んだ検索（外側が2行） | 0.5 秒 |

氏名で絞ると速くなるのが、この診断を決めた。外側の行数に比例している。
「絞り込めば速い」ので、手元で軽く触るだけでは気づけない。

**対応**: 関数を `WITH ... AS MATERIALIZED` に切り出し、年度で絞った
状態で1回だけ評価させる。`AS MATERIALIZED` を外すとプランナが
元の形に畳み戻せるため、この指定は飾りではない。

**対策後の実測（実行④）。** 同じ SELECT・同じ `ORDER BY`・同じ `LIMIT` で、
`f_person_season_state` の置き場所だけを変えて比べた。

| 書き方 | 時間 |
|---|---|
| 結合の内側に関数を置く（対策前） | 438.9 秒 |
| `WITH ... AS MATERIALIZED`（対策後） | **0.7 秒** |

同じデータ（`.pgdata` の複製、Person 2,745 人）に対する比較。
秒数そのものはデータ量と機械に依存するので追試の対象ではないが、
**外側の行数に比例する再評価が消えた**ことがこの比で読める。
`LIMIT` だけを付けて比べると入れ子ループが途中で打ち切られて 3 ミリ秒に
見えるため、`ORDER BY` を外してはいけない。

意味論が変わっていないことはテストで固定してある。

→ `tests/12_drilldown.test.ts`「年度を指定すると、その年度の母集団に入る人だけが返る」

### A-14. 取り下げられた応募が「選考中」として催促され続けていた ★影響大

実行③で作った `/applications/[id]` を初めて開いたら、9か月前に取り下げ
られた応募が **「選考中」** と表示されていた。

結末がどこにも定義されておらず、画面2枚がそれぞれ同じラダーを
自前で書いていたのが原因。

```
合格 → 辞退 → 不合格 → （どれでもなければ）選考中
```

「どれでもなければ選考中」は、遷移が1行も無い応募をすべて選考中にする。
選考開始前に取り下げられた応募（`voided_at` あり、遷移なし）がそこに落ちる。

**根は表示ではなく、軸が1本足りないことだった。**

| 軸 | 述語 | 意味 |
|---|---|---|
| 数えるか | `v_countable_applications` | 応募が起きた事実として木に数えるか |
| 動いているか | （無かった） | いま誰かが判断すべき状態にあるか |

選考開始前の取り下げは「数えるが、動いていない」。この組み合わせを表す
述語が無かったため、`v_countable_applications` が両方の役を兼ねていた。
判断待ち・保留がそれを母集団にしていたので、**取り下げた相手の判断を
面接官に催促し続ける**形になっていた。③（いま何が起きているか）と
④（次に何をすべきか）の両方を誤らせる。

同じ問い合わせを見直して、隣接する3つも同じ根で壊れていた。

- `getUnassignedSummary` は `applications` にも `persons` にも結合して
  いなかった。すぐ隣に並ぶ判断待ちの一覧とは母集団が違う。同じ画面の
  2つの数字が別の母集団から出ていた。個人情報削除を受けた人の評価も数える
- `getConflicts` は生の `applications` に結合しており、
  無効化済みも、個人情報削除を受けた応募者の**氏名**も出しうる形だった
- `getHeldEvaluations` は判断待ちと同じ

**対応**: `db/migrations/0011_application_outcome.sql`。

- `v_application_outcome` … 応募の結末。`v_application_state` の上には
  作れない。あれは `v_countable_applications` を母集団にしているため、
  名寄せ誤りで無効化された応募には行が無く、「合格したあとに無効化された
  応募」の結末を引けなくなる。起きた事実は数えるかどうかと無関係に残す（C-12）
- `v_active_applications` … いま動いている応募。判断待ち・保留・
  担当未割当・利益相反の母集団をここに揃えた

結末の判定順は **辞退 → 合格 → 不合格 → 無効化 → 選考中**。

- 辞退が合格より先。合格後に辞退した応募の結末は辞退で、席は空く。
  ファネルの `net_accepted_cum` と同じ扱いにした。到達した事実のほうは
  `v_application_state.is_accepted` に残っており、消していない
- 無効化は最後。合格・不合格・辞退という起きた事実を上書きしない。
  無効化は「その後どう扱うか」の話であって、結末そのものではない

画面側のラダーは両方消し、`OUTCOME_LABEL` で表示名に写すだけにした。
「集計対象外」は結末とは別の軸なので、別のバッジとして残してある。

デモにも登場人物を1人足した（C-15）。**この形は、実行①〜③のデモが

### A-15. デモの出来事が、指定した日の1日前に起きていた

A-14 の確認で登場人物の画面を開いたら、`persons.note` に「2026-05-18 に
識別された」と書いたつもりの人が **2026/05/17** と表示されていた。

`src/seed/demo.ts` の `at()`。

```ts
const d = new Date(`${base}T00:00:00+09:00`)  // その瞬間の UTC 日付は前日
d.setUTCHours(hour - 9, minute, 0, 0)          // 前日のまま時刻だけ入る
```

JST 深夜を基準に取ると、その瞬間の UTC 日付は前日である。
そこへ `setUTCHours` で時刻を入れるので、**どの時刻を渡しても指定日の
1日前**になっていた。A-1（`::date` が接続のタイムゾーンに依存する）と
同じ間違いを、集計ではなくデータの生成側でやっていた。

**表に出なかった理由が重要である。** 応募は
`at(plan.applicationOpen, day, ...)` から作るので、`day = 0` の応募は
応募開始日の前日に発生していた。ところが `f_funnel_daily` は応募開始日
より前の出来事を初日に寄せる（0004 の `clamped`）。**丸め込みが辻褄を
合わせてしまい、集計値としては正しく見えていた。**
実行②の「表示の丸めで注記が画面上の嘘になった」と同じ形である。

**対応**: 暦日の足し算は UTC 深夜を基準に行い、`YYYY-MM-DD` を返す。
時刻はタイムゾーンつきのリテラルを組み立てて与え、暦の解釈を `Date` に
任せない。`partner_reaches.reach_date` の組み立ても同じ理由で直した。

直した副作用として、**年度のどの期間にも入らない接点が0件になった。**
あの形は、このずれが偶然に作っていたものだった。年度の切れ目に届く連絡は
実データでは必ずあるので、登場人物に1件を明示的に置き直した（C-15）。
**デモの経路が「バグによって偶然踏まれていた」形で、バグを直すと
検証したい経路まで一緒に消える。**

→ `tests/13_demo_coverage.test.ts`「デモの出来事が、年度の期間より前に起きていない」
→ `tests/13_demo_coverage.test.ts`「団体経由の接点と、年度に紐づかない接点がある」

### A-16. 年度を1つ指定すると、集計が 9000 倍遅くなった ★影響大

実行⑥。0012 で作った `v_forest_season_activity` を画面から呼んだところ、
**開発サーバが応答しなくなった。** CPU を 64% 使い続けており、
止まっているのではなく回り続けていた。

書いた直後に測ってはいた。`SELECT count(*) FROM v_forest_season_activity`
が 19 ミリ秒だったので、速いと判断した。**その測り方が間違っていた。**

| 測り方 | 実測 |
|---|---|
| 全件（`WHERE` なし） | 19 ミリ秒 |
| 年度を1つ指定（リテラル） | 177,694 ミリ秒 |
| 年度を1つ指定（パラメータ） | 176,656 ミリ秒 |

リテラルでもパラメータでも同じなので、プリペアドの汎用プランの話ではない。
**述語のプッシュダウンである。** `season_id = X` が各 CTE の内側へ降りると、
プランナは「対象は数行」と見積もってハッシュ結合をやめ、入れ子ループを選ぶ。
その内側に居るのが `v_open_tasks` と `v_application_state` で、どちらも
`v_effective_status_histories`（再帰 CTE）を通る。**外側の行ごとに再帰が
回り直す。** A-8・A-11 と同じ構図である。

**A-11 と向きが逆である。** あちらは「氏名で絞ると速いので、手元で軽く
触るだけでは気づけない」だった。だから実行③以降「一覧は必ず素の状態
（絞り込みなし）で開いて確かめる」を手順にしていた。今回はその手順
どおりに測って、**絞り込みなしだけが速い**という逆の形を見逃した。
片側だけを測る限り、どちらの向きも取り逃す。**両方で測る。**

**対応**は2つある。どちらも「絞り込みを、高い供給元まで降ろさない」。

1. `v_forest_season_activity` の供給元 CTE（`forest_person` / `countable` /
   `open_tasks`）を `MATERIALIZED` にした。`MATERIALIZED` はプッシュダウンを
   禁じる指定そのもので、供給元を1回ずつ走ってから畳む。
   年度を1つしか見なくても全件を1回走ることになるが、爆発しないほうを取る。
   **177 秒 → 0.15 秒。** 全件は 0.02 秒のままで、桁の差が消えた
2. `v_open_tasks` の `season_id` を、応募（`a.season_id`）ではなく
   選考ステップ（`ss.season_id`）から取るようにした。応募側から取ると
   同じ述語が `v_active_applications` を通って再帰 CTE まで降りる
   （0.074 秒 → 0.413 秒）。ステップ側なら小さな表で止まる（0.074 → 0.076 秒）。
   既存の `getPendingEvaluations` も `ss.season_id` で絞っており、そちらに揃う形でもある

`v_open_tasks` を丸ごと `MATERIALIZED` で押さえる案も測った。絞り込みの
有無によらず 1.05 秒になり、全応募を毎回実体化する分が節約を上回った。
**採らなかった案も測ってから捨てる。**

固定の仕方について。**実行時間はテストに書かない。** データ量とマシンに
依存する数字を残しても追試できないし、閾値は環境が変われば嘘になる
（「作り物のデータから出た数字をドキュメントに残さない」）。
残すのは**プランが崩れない形のほう**なので、ビュー定義そのものを見張る。

→ `tests/15_forest_and_tasks.test.ts`「森×年度の集計は、供給元を1回だけ走る形を保っている」
→ `tests/15_forest_and_tasks.test.ts`「やることの年度は、選考ステップ側から取っている」
→ `tests/15_forest_and_tasks.test.ts`「どちらから取っても、年度の値そのものは変わらない」

### A-18. 保留と利益相反が重なると、やることが二重に出ていた

母集団を `v_open_tasks` の `'reassign'` に揃えようとして数え直したら、
**同じ評価が2行あった。**

```
unhold    … state = 'held'（利益相反を見ていない）
reassign  … 利益相反 AND state IN ('pending','held')
```

0012 では `'evaluate'` から利益相反を除いてある。そのとき自分でこう書いた。

> 利益相反が出ている評価に「評価してください」とは出さない。
> そこでやるべきことは担当の差し替えであって、評価ではない。
> **同じ評価を2種類のタスクとして2回出すと、件数が二重に見える。**

**同じ手当てを `'unhold'` にしていなかった。** 保留を解いても、面接官が
紹介者のままなら次にやることは差し替えである。順序が逆になっていた。

**表に出ていなかった理由。** デモに「保留 かつ 利益相反」の組み合わせが
無かった。乱数で生まれた利益相反はすべて `submitted` で、明示的に置いた1件は
`pending` だった。**組み合わせを1つ置き忘れると、分岐は静かに死ぬ。**
実行⑥で `reassign` そのものが一度も踏まれていなかったのと同じ形である
（C-19）。**種別ごとに条件を足す設計は、組み合わせの数だけ穴が開く。**

**対応**: 0013 で `'unhold'` にも同じ `NOT EXISTS` を付けた。
0012 は適用済みなので編集せず、`CREATE OR REPLACE VIEW` で置き換えた
（列の並びも型も変えていないため、依存する `v_forest_season_activity` を
作り直す必要が無い）。

固定の仕方を、個別の組み合わせではなく**ビュー全体の性質**にした。
種別を足すたびに同じ穴が開くので、「1つの評価は1件のやることにしか出ない」を
デモ全体に対して検査する。

→ `tests/15_forest_and_tasks.test.ts`「保留中の評価に利益相反があっても、やることは1件だけ出る」
→ `tests/13_demo_coverage.test.ts`「1つの評価が、2件のやることに出ていない」

### A-19. 「根拠は必須」が、空白の種類によって破れていた

実行⑥。E2（点と根拠を画面から保存する）を作り、空の根拠が弾かれることを
テストで確かめようとしたら、**改行だけの根拠が保存できた。**

原因は `btrim` の既定値である。

```sql
btrim(rationale) <> ''      -- 既定は btrim(rationale, ' ')。半角スペースだけ
```

通っていたのは次の形である。

| 入力 | 当時 |
|---|---|
| `''`（空文字） | 弾かれる |
| `'   '`（半角スペース） | 弾かれる |
| 改行だけ / タブだけ | **通る** |
| 全角スペースだけ | **通る** |

原典のコメントはこう書いている ――「空文字が通ると『必須にした』という
設計意図が形骸化する（資料5-3）」。**意図は正しく、実装が届いていなかった。**
B 節の表に「`rationale` が空白のみは不可」と書いてあるのに、
実際には空白のみで通る形が3つあった。

**これは「記録が実装より厳密に見える」形である。** 読んだ人は守られていると
思って確認をやめる。DECISIONS.md の冒頭がいちばん警戒している壊れ方で、
B 節の表そのものが一度それで破れている。

**表に出なかった理由。** 画面から入力できなかったので、根拠は
デモの生成コードとテストからしか入らず、どちらも実文を入れていた。
**入力欄を作った瞬間に踏める穴になった。**

**対応**（0015）: 落とす文字を明示した。

```sql
CHECK (btrim(rationale, E' \t\n\r　') <> '')
```

0001 は適用済みなので編集せず、制約を落として付け替えた。2つ残すと
どちらが効いているかが読んで分からない。既存の行が違反しないことは
`pnpm db:reset` と全テストで確かめた（デモの根拠はすべて実文）。

画面（`required` 属性）で弾く形にはしなかった。**判定を記録層に1つだけ置く。**
実際に `required` を外して全角スペースを送り、`rationale_blank` が返ることを
実データで確かめている。

→ `tests/20_score.test.ts`「根拠が空だと拒否される（空白・改行・タブ・全角スペースも）」
→ `tests/20_score.test.ts`「前後に空白があっても、中身があれば保存できる」

## C. 構造の整理

### C-1. 最終ステップ判定を1箇所に畳んだ

「最終ステップへの advance = 合格」の判定が

```sql
ORDER BY ss.sort_order DESC LIMIT 1
```

という相関副問い合わせとして4箇所に複製されていた（原典の
`v_person_state` に1箇所、`academy_views_revised.sql` に3箇所）。
合格の定義が4箇所にあると、1箇所だけ直したときに誰も気づかない。
`v_final_selection_step` に集約した。

→ `tests/04_funnel.test.ts`「中間ステップへの advance では幹にならない」

### C-2. 森の観測窓 90 日を引数にした

`v_partner_reach_summary` は「最終リーチ日 + 90 日」を定数で埋め込んでいた。
90 は集計定義そのものであり、コードに埋めると変更履歴が残らない（原則4）。
`f_partner_reach_summary(attribution_window_days integer DEFAULT 90)` にした。
`first_reach_on` / `last_reach_on` も返すようにして、窓の根拠を見えるようにした。

### C-3. `pgcrypto` への依存を外した

`gen_random_uuid()` は PostgreSQL 13 以降コアの関数で、拡張を要さない。
拡張を要求すると、それが使えない環境でスキーマ全体が適用できなくなる。

### C-4. `partners` を `touchpoints` より前に定義した

原典は `touchpoints` を先に定義し、`ALTER TABLE` で外部キーを後付けしていた。
依存順に並べ替えて `ALTER` を不要にした。

当初これを「定義の位置以外に差はない」と書いていたが、誤りだった。
原典は `ADD CONSTRAINT touchpoints_partner_fk` と制約名を明示している。
インラインの `REFERENCES` に置き換えると PostgreSQL が
`touchpoints_partner_id_fkey` と自動命名し、制約名で分岐するコード
（このリポジトリのテストがまさにその書き方をしている）で挙動が変わる。
インラインでも `CONSTRAINT touchpoints_partner_fk` と明示して名前を揃えた。

### C-5. 利益相反に「面接官＝応募者」を追加した

原典は紹介者のケースだけを見ていた。卒業生スタッフが再応募すれば
面接官と応募者が同一人物になりうる。紹介より直接的な相反が素通りしていた。
`conflict_type` 列で2種を区別する。

### C-6. 日付系列の生成を timestamp 経由にした

`generate_series(date, date, interval)` は date を timestamptz に暗黙変換し、
セッション TZ を一往復する。`::timestamp`（TZ なし）を経由して往復を消した。

### C-7. 定義との食い違いを塞いだ（0007）

自己レビューで、原典の定義が述べていることと実装が食い違う箇所が3つ出た。
いずれも定義のほうが正しいと判断して実装を寄せた。

**(1) `v_person_season_state` が Person × Season で複数行を返していた。**
原典は「年度別の現在地（Person × Season 単位）」と定義しており1人1行が前提。
ところが A-2 で同一年度に同一 Person の集計対象応募が2件ありうるように
なった（取り下げて出し直した場合）のに、結合が 1:1 のままだった。
同じ人が同じ年度に「木」と「幹」の2行で現れ、段ごとに数えると
1人が2段に同時に立つ。応募をまたいで最高到達点を取る形に直した。

A-2 を入れたときに結合の多重度が変わることを見落としていた。
修正が別の場所を壊す典型で、D-2 の「木が1人で2件になる」という記述は
この破綻までは含んでいなかった。

**(2) 訂正が応募をまたげた。** `corrects_history_id` に同一応募の制約がなく、
応募Yの行から応募Xの合格を打ち消せた。しかも有効性判定は打ち消された行を
黙って落とすので、応募Xの担当者には何が起きたか分からない。
原則5の「訂正」は同じ応募の記録に対する操作なので、トリガで縛った。

**(3) 選考ステップが年度をまたげた。** 評価軸とステップの整合は 0001 の
トリガで見ていたが、その1段上（ステップと応募の年度）が空いていた。
2026年度の応募に2027年度のステップを指す評価や遷移を入れられ、
応募0件の年度のステップ別集計に到達数が立った。

### C-10. マイグレーションの適用と記録を同一トランザクションにした

### F-1. 「クライアント JavaScript を配信していない」は事実と違った ★記録の訂正

`HANDOFF.md` の技術構成にこう書いてあった。

> Next.js App Router（**サーバコンポーネントのみ、`'use client'` が0件**）。
> クライアント JavaScript を一切配信していない。

**前半は正しく、後半は誤りである。** 実行⑥で書き込みを足す前に、
それがクライアント境界に触れるかを確かめようとして気づいた。
配信されている HTML を見ると `<script src>` が並んでいる。

```
/_next/static/chunks/…react-dom…js
/_next/static/chunks/…react-server-dom-turbopack…js
…（開発サーバでは next-devtools も）
```

App Router は RSC のペイロードを流し込むために React の実行時を必ず配る。
`'use client'` が0件でも「JS を配信していない」ことにはならない。

**この誤りが何を招きかけたか。** 「JS を1バイトも配っていない」という前提で
考えると、フォームの送信すら境界の新設に見える。実際には素の
`<form action={...}>` はサーバコンポーネントに置けて、`'use client'` は

### C-28. 実年度と創作のデモを同じ DB に置けなくした

実行⑦。**実データの受領で初めて表に出た衝突である。**

#### 衝突そのものより、衝突を避けたときのほうが危ない

素直な直し方は、デモ側を「既にある年度は作らない」にすることだった。
**これは採らない。** 衝突しなくなる代わりに、**創作の応募・評価・判定が

止まって落ちるほうがましである。**辻褄が合っている＝正しい、ではない**
（実行⑥で踏んだ「丸め込みが欠陥そのものを隠す」と同じ形）。

デモ側の年度をずらす案も採らない。ずらしても**次の実年度（2027）で同じことが
起きる。** 年度をずらすのは、衝突の時期を先送りするだけである。

#### 直し方 ―― 環境ごとに入るシードを分けた

`*.example.sql` が「サンプルの環境にだけ入る」という仕組みは既にあった。

```

*.example.sql                   サンプルの環境にだけ入る
*.production.sql                本番の環境にだけ入る  ← 追加

`includeExamples` のときに `.production.sql` を外す。

pnpm db:reset   サンプル＋デモ。実年度は入らない
seed(db)        本番。実年度が入る。デモは入らない
```

**「サンプルを入れる」と言った環境に、実在の記録を入れない。**
この規則は年度に限らない。実データを取り込む段（`DATA-INTAKE.md` 3節の 4）でも
同じ境界を使う。

固定しているテストは `tests/22_reference_season.test.ts` の

### C-29. ロゴとパレットを NEO ACADEMIA ブランドに差し替えた

実行⑦。2026-08-07。**依頼者の指示で、保留していた生成元が決まった。**

これまで `app/tokens.css` は `basic/DESIGN.md`（Notion のブランド分析）から
生成されており、`design.md` は soft green を求めていた。**生成元が未決**だったため
「画像から色を起こして推測で埋めない」を守って触っていなかった（HANDOFF 7節）。
指示によりこの保留が解けた。

#### 推測していない

色は**ブランド規定に書かれた値をそのまま置いた。** ロゴ画像から色を吸ったのではない。

```
ネオンイエロー #F0F000 / ネオンピンク #F03090
ネオンシアン   #00C0F0 / ネオングリーン #50F000 / ネオンレッド #F01010
ベース         白 #FFFFFF / 黒 #0A0A0A / グレー #707070 / 罫線 #E5E5E5
```

**★ 派生させた値が6つある。** ネオン色は白背景の文字として読めない
（`#F0F000` は特に）。規定の色相を保ったまま暗くしたものを、
`link-blue` / `link-blue-pressed` / `brand-orange-deep` /
`semantic-success` / `semantic-warning` / `semantic-error` に当てた。
**`DESIGN.md` の中で ★ 印を付けて、規定の値と区別できるようにしてある。**

#### 「色は線、面は黒」をトークンの側で強制した

ブランドの最重要原則である。**面をアクセント色で塗らない。**

そこで**面に使われるトークンを全部、白か黒か極薄のグレーに倒した。**

- `primary` / `brand-navy` / `brand-purple*` → 黒（塗ってよい唯一の色）
- `card-tint-*`（9個の淡色）→ 白と極薄グレー

これで CSS 側を1行も直さなくても、**アクセント色の面塗りが構造的に作れなくなる。**
以後 `card-tint-*` を背景に使っても色は出ない。

#### 色を消したら一覧が読めなくなった ―― 面から線へ移した

淡色の面塗りを消した結果、**やることの種別が全部ただの黒文字になった。**
色を消すのではなく面から線へ移すのが規定の意図なので、
`app/base.css` の末尾でバッジを塗りから**左の2px 線**へ組み替えた。

```
評価する      シアン      担当を替える  ピンク
担当を決める  イエロー    保留を解く    グレー（停止状態なので色を当てない）
```

規定のグラフ系列順（シアン → ピンク → イエロー → グリーン）に合わせてある。

選択中の行も淡い面だったので、**黒い線**に変えた。期限超過（赤）とは別の辺を
使うので、両方立っても打ち消し合わない。

#### ロゴ

ブランド名は**必ずロゴ画像で出す。** 極太テキストで「NEO ACADEMIA」と書くと
ロゴと競合する（規定）。`Youth<span>DB</span>` のワードマークを
`public/brand/logo_black.png` に置き換えた。比 3.15:1 を崩さないよう
`width` だけ与えて `height: auto` にしてある。白版も
`public/brand/logo_white.png` に入れてある（黒背景で使う）。

#### `basic/` を変更したことについて

`CLAUDE.md` 5節は「`basic/` は変更しない」と定めているが、
これは**原典の SQL** に対する規律である（`basic/*.sql`）。
`basic/DESIGN.md` はトークンの生成元であり、`pnpm tokens` が読む。
**色を変える正しい経路はここを直すこと**で、`app/tokens.css` の手編集ではない。

固定しているテストは無い。**色に対する自動テストは置いていない。**
置くなら「アクセント色が背景に使われていないこと」の検査だが、
CSS の静的解析になり、いまの `node:test` の枠から外れる。TODO(MVP)。

### C-38. デプロイ先が決まった ―― マネージド Postgres（Supabase）。PostgreSQL アダプタを実装した

実行⑧。止まっていた3件（`HANDOFF.md` 5節）のうち1件（デプロイ先）に、

（マネージド Postgres）を選んだ。** 費用と運用体制の判断であり、
推奨はあくまで見立てだったので、そのまま従う。

#### pg アダプタ（`src/db/postgres.ts`）

`Db` インターフェイスは `query`/`exec`/`close` の3つだけなので、
差し替えは `src/db/server.ts` の該当箇所（元から「throw する」と
書かれていた場所）に閉じた。`exec` はパラメータ無しの `query()` が
simple query protocol を使う性質を利用し、PGlite の `exec` と同じく
`;` 区切りの複数文をそのまま流せる。

#### 直接接続は IPv6 専用で届かなかった。プーラーへ切り替えた

Supabase の直接接続ホスト（`db.<ref>.supabase.co`）は AAAA レコードしか
持たない。開発機に IPv6 の外向き経路が無く `ENOTFOUND` になった。
Connection Pooler（Supavisor）は IPv4 で届く上、サーバレスでの
コネクション数管理にも向くため、そもそも Pilot の構成としてはこちらが正しい。

Session pooler（5432）と Transaction pooler（6543）の2つがあり、
**Session pooler を選んだ。** セッション単位の `SET`（後述のタイムゾーン
設定）がトランザクションをまたいで保持される保証が要るため。
Transaction pooler はコネクション数をさらに絞れるので、
Pilot の規模で問題が出たら見直す（Technical Debt）。

#### `SET` を接続イベントで投げると競合した

最初は `Pool` の `'connect'` イベントで `SET TimeZone = 'Asia/Tokyo'` を
fire-and-forget していたが、プールがそのクライアントを次のクエリに
使い回すタイミングと競合し、「client.query() が実行中にまた呼ばれた」という
非推奨警告（pg 9 系で削除予定）が出た。起動パラメータ
（`options: '-c TimeZone=Asia/Tokyo'`）に切り替えて解消した。
**目視ではなく、実接続に対して `tests/00_environment.test.ts` を
走らせて再現・修正・再確認した。**

#### 環境テストを実接続に対しても走らせる形にした

`tests/00_environment.test.ts` の元のコメントは「本番へ初めて適用する前に、
同じ検査を本番の接続に対して走らせること」と書いていたが、手順が無かった。
`DATABASE_URL` が設定されていれば同じ検査を Supabase 接続に対しても

`gen_random_uuid()`・`UNIQUE NULLS NOT DISTINCT`・式インデックス・
