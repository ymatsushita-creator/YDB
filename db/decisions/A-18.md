### A-18. 保留と利益相反が重なると、やることが二重に出ていた

実行⑥。「担当を替える」を画面から実行できるようにする作業中、操作できる
母集団を `v_open_tasks` の `'reassign'` に揃えようとして数え直したら、
**同じ評価が2行あった。**

```
unhold    … state = 'held'（利益相反を見ていない）
reassign  … 利益相反 AND state IN ('pending','held')
```

0012 では `'evaluate'` から利益相反を除いてある。そのとき自分でこう書いた。

> 利益相反が出ている評価に「評価してください」とは出さない。
> そこでやるべきことは担当の差し替えであって、評価ではない。
> **同じ評価を2種類のタスクとして2回出すと、件数が二重に見える。**

**同じ手当てを `'unhold'` にしていなかった。** 保留を解いても、面接官が
紹介者のままなら次にやることは差し替えである。順序が逆になっていた。

**表に出ていなかった理由。** デモに「保留 かつ 利益相反」の組み合わせが
無かった。乱数で生まれた利益相反はすべて `submitted` で、明示的に置いた1件は
`pending` だった。**組み合わせを1つ置き忘れると、分岐は静かに死ぬ。**
実行⑥で `reassign` そのものが一度も踏まれていなかったのと同じ形である
（C-19）。**種別ごとに条件を足す設計は、組み合わせの数だけ穴が開く。**

**対応**: 0013 で `'unhold'` にも同じ `NOT EXISTS` を付けた。
0012 は適用済みなので編集せず、`CREATE OR REPLACE VIEW` で置き換えた
（列の並びも型も変えていないため、依存する `v_forest_season_activity` を
作り直す必要が無い）。

固定の仕方を、個別の組み合わせではなく**ビュー全体の性質**にした。
種別を足すたびに同じ穴が開くので、「1つの評価は1件のやることにしか出ない」を
デモ全体に対して検査する。

→ `tests/15_forest_and_tasks.test.ts`「保留中の評価に利益相反があっても、やることは1件だけ出る」
→ `tests/13_demo_coverage.test.ts`「1つの評価が、2件のやることに出ていない」
