### C-11. 森を画面に出すにあたって足したもの（0009）

原典の `v_partner_reach_summary` は実装されていたが、どの画面からも
読まれていなかった。(4)流入元を作るにあたって、まず何を数えているのかを
テストで固定した。集計そのものは定義どおりに動いていた
（推定リーチの合計、接触機会の行数、観測窓、JST 境界、削除済み Person の除外）。

足したのは次の3つ。

**(1) `f_partner_reach_persons`（0009）。** `identified_count` は団体×年度の
実人数で、**行をまたいで足せない**。同じ人が2つの団体から接触されていれば
両方の行で1と数えられ、同じ団体が複数年度にリーチしていれば観測窓が重なりうる。
年度全体の実人数を出すつもりで合計すると、重複したまま増える。

画面側で数え直すこともできるが、それだと観測窓の定義がアプリと
データベースの二箇所に散る。人の集合まで戻る関数をデータベース側に置いた。
定義が2箇所（`f_partner_reach_summary` と `f_partner_reach_persons`）に
ある状態は残るので、団体×年度ごとの人数が一致することをテストで固定してある。

デモデータの2027年度では、団体別の識別の合計が50人、年度全体の実人数が48人になる。
画面はこの2つを並べたうえで、一致しないことと理由を注記に書いている。

→ `tests/11_partner_reach.test.ts`「identified_count は行をまたいで足せない」、
   11「団体・年度・窓の組み合わせが変わっても一致する」、
   11「団体別の行は年度で絞られ、年度全体の実人数は重複排除される」

**(2) 年度に紐づかないリーチの明示。** `partner_reaches.season_id` は NULL 可で、
年度で絞ると表から消える。消えたことが分からないと、推定リーチの合計が
実際より小さいことに誰も気づけない。件数と推定値を画面に出す。
接点側の「未割当」（原典が(4)での表示を指示しているもの）と同じ扱いにした。

→ 11「年度に紐づかないリーチは件数として見えるところに出す」、
   11「どの年度にも属さない接点を未割当として数える」

**(3) 出さないと決めたもの: 推定リーチに対する識別率。**
一度 KPI として置いたが外した。分母は推定した接触機会、分子は実人数で、
単位も数え方も違う。定義の違うものを割った値は分析にならないという理由で
日次の 林 → 木 転換率を削除している（D-3）のに、同じ性質の数字を
森で作っていた。`estimated_reach` が推定値でなくなるまで出さない。

**あわせて、アトリビューション3方式を1つの表にした。** 3方式は同じ実人数を
違う重みで配るので、列の合計は3つとも一致する。当初 SQL 側で小数2桁に
丸めていたところ、行ごとの誤差が積もって線形の縦計だけ 885.99 になり、
「合計は一致する」という注記が画面上で嘘になっていた。丸めをやめ、
合計行は丸める前の値から作る。

→ 11「アトリビューション3方式は合計が一致し、内訳だけが違う」

なお森の観測窓は `REACH_WINDOW_DAYS`（90日）として林の
`ACTIVE_WINDOW_DAYS` とは別の定数にした。値は同じだが別の概念で、
片方を運用データに合わせて動かしたときにもう片方まで動くと困る。
どちらも仮の値である。
