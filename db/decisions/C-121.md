### C-121. ★★ 説明のつかない本番書き込みを特定した ―― 押せるボタンを渡していた

実行⑬の最後、本番へ 0033〜0035 が**こちらが流す前に**適用されていた
（`applied_at` = 2026-08-13T07:20:11Z。明示実行は 07:21:00）。
実行⑬は「何が適用したのか特定できていない」と書いて引き継いだ。**特定した。**

#### 走ったのは `pnpm db:migrate:production` そのもの ―― 依頼者の手元から

決め手は `xmin`（行を書いたトランザクションの番号）である。

```
xmin 2851 / 2852 / 2853   0033・0034・0035        07:20:11
xmin 2854               2期の特別選考1段＋9軸（seed 0005 が入れるもの）
```

**`migrate()` だけを呼ぶ経路では 2854 が起きない。** `seed:demo-season --remote` は
参照データを入れないので、0035 の直後の連番で 0005 が入っている以上、
走ったのは **migrate と seed を両方やる `db:migrate:production`** である。

その41秒前、実行⑬は最終報告の末尾に **```bash の塊として
`pnpm db:migrate:production` を出していた。** この環境では、その塊は
**押せるボタンとして描画される。** 14秒後に依頼者から「やれ」が届いている。

否定できた経路 ―― CI は存在しない（`.github` が無い）。`migrate()` の呼び出しは
4箇所しか無く（`testing.ts` / `server.ts` の PGlite ・ `db-reset`（DATABASE_URL があれば拒否）・
`seed-demo-season --remote` ・ `db-migrate-production`）、**アプリの実行経路と
`next build` からは呼べない。** Vercel は `VERCEL=1` でデモ（PGlite インメモリ）。

★ **穴は「意図しない経路」ではなく、こちらが渡した塊だった。**
実行できる形で本番への書き込みを渡した時点で、それは自分が流したのと同じである。
**渡したあとの本番の状態を、自分の実行記録ではなく本番に聞く。**

#### ★ もう1つの誤り ―― 控えを、書き込みの**後**に取っていた

実行⑬は 07:20:55 に `pnpm db:backup` を取り、その控えを「適用前の姿」として
引き継いだ。**実際には 07:20:11 の書き込みより後**で、適用前の姿ではない。
さらに控えの `schema_migrations 35` を「0032まで適用済み」と読んだ
（**35行＝0035まで**）。行数を数えて段数を言い当てようとしたのが誤りである。

#### 塞いだもの

```
schema_migrations.applied_by   適用した接続の名乗り（application_name）を記録する。
                               中身は「道具・pid・機械」。同じコマンドでも
                               実行が違えば名前が違うので、自分か他人かがその場で分かる
openPostgres()                 接続に名乗らせる（youthdb <script>#<pid>@<host>）
db:migrate:production          ① **書き込む前に自分で控えを取る**（順番を記憶に委ねない。
                                  seed は冪等でも書き込みであって読み取りではない）
                               ② 適用の前後で帳簿の**末尾を名前で**印字する。
                                  0本のときは「すでに当たっている、が、
                                  名乗りが自分でなければ別の誰かが流している」と言う
```

★ `schema_migrations` は `migrate()` 自身の帳簿なので、**マイグレーション番号で
育てられない** ―― 新しい DB では帳簿を作ってから 0001 を流すため、番号で足すと
列が無いまま INSERT が走る。だから列を足すのは `migrate()` の起動処理で、
既存の本番には `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` で追いつかせる。

★ `application_name` は**印字可能なASCIIしか通らない**（それ以外は PostgreSQL が
`\xNN` へ置き換える）。名乗りに日本語を使わない ―― テストで踏んだ。

★ これは犯人探しの仕掛けではない。**次の実行が同じ1時間を使わないための帳簿**である。

#### ★ 同じ穴を、塞いだ道具の側でもう一度踏んだ

本番へ流した1回目に「**適用前 ―― 帳簿がまだ無い**」と出た。本番の帳簿は 0035 まで
35行あり、**嘘である。** 適用前の状態を読む問い合わせが `applied_by` を素直に
選んでいたためで、**その列を足すのは `migrate()` の中**だから読む時点ではまだ無い。
「列が無い」で落ちた例外を、catch が「帳簿が無い」へ翻訳していた。

`to_jsonb(m)->>'applied_by'`（列が無ければ NULL）に直し、`ledgerTail()` として
`src/db/migrate.ts` へ移してテストの下に置いた。

★ **状態を伝える道具が嘘をつくのは、状態を読まないより悪い。**
読み違えを塞ぐために作った表示が、別の読み違えを作っていた。

検証: `tests/51_migration_provenance.test.ts`（名乗りが残る／名乗りが無くても通る／
列を持たない古い帳簿でも列を足して進む／**その帳簿を読めること**／帳簿が無ければ null）。
本番へ適用し、控えの前後で変わった表を数えた。
