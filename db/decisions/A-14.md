# A-14

### A-14. 取り下げられた応募が「選考中」として催促され続けていた ★影響大

実行③で作った `/applications/[id]` を初めて開いたら、9か月前に取り下げ
られた応募が **「選考中」** と表示されていた。

結末がどこにも定義されておらず、画面2枚がそれぞれ同じラダーを
自前で書いていたのが原因。

```
合格 → 辞退 → 不合格 → （どれでもなければ）選考中
```

「どれでもなければ選考中」は、遷移が1行も無い応募をすべて選考中にする。
選考開始前に取り下げられた応募（`voided_at` あり、遷移なし）がそこに落ちる。

**根は表示ではなく、軸が1本足りないことだった。**

| 軸 | 述語 | 意味 |
|---|---|---|
| 数えるか | `v_countable_applications` | 応募が起きた事実として木に数えるか |
| 動いているか | （無かった） | いま誰かが判断すべき状態にあるか |

選考開始前の取り下げは「数えるが、動いていない」。この組み合わせを表す
述語が無かったため、`v_countable_applications` が両方の役を兼ねていた。
判断待ち・保留がそれを母集団にしていたので、**取り下げた相手の判断を
面接官に催促し続ける**形になっていた。③（いま何が起きているか）と
④（次に何をすべきか）の両方を誤らせる。

同じ問い合わせを見直して、隣接する3つも同じ根で壊れていた。

- `getUnassignedSummary` は `applications` にも `persons` にも結合して
  いなかった。すぐ隣に並ぶ判断待ちの一覧とは母集団が違う。同じ画面の
  2つの数字が別の母集団から出ていた。個人情報削除を受けた人の評価も数える
- `getConflicts` は生の `applications` に結合しており、
  無効化済みも、個人情報削除を受けた応募者の**氏名**も出しうる形だった
- `getHeldEvaluations` は判断待ちと同じ

**対応**: `db/migrations/0011_application_outcome.sql`。

- `v_application_outcome` … 応募の結末。`v_application_state` の上には
  作れない。あれは `v_countable_applications` を母集団にしているため、
  名寄せ誤りで無効化された応募には行が無く、「合格したあとに無効化された
  応募」の結末を引けなくなる。起きた事実は数えるかどうかと無関係に残す（C-12）
- `v_active_applications` … いま動いている応募。判断待ち・保留・
  担当未割当・利益相反の母集団をここに揃えた

結末の判定順は **辞退 → 合格 → 不合格 → 無効化 → 選考中**。

- 辞退が合格より先。合格後に辞退した応募の結末は辞退で、席は空く。
  ファネルの `net_accepted_cum` と同じ扱いにした。到達した事実のほうは
  `v_application_state.is_accepted` に残っており、消していない
- 無効化は最後。合格・不合格・辞退という起きた事実を上書きしない。
  無効化は「その後どう扱うか」の話であって、結末そのものではない

画面側のラダーは両方消し、`OUTCOME_LABEL` で表示名に写すだけにした。
「集計対象外」は結末とは別の軸なので、別のバッジとして残してある。

一度も生成していなかった。** 同じ見落としの4回目にあたる。
