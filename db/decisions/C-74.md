### C-74. 2期の実データを本番へ入れた（0023）

依頼者の指示（実行⑩、繰り返し）―― 実データを入れる。

★★ **方針の変更である。** 同じ実行の前半で依頼者は
「生年月日を集める」（記録層は変えない）を選んでいた（C-61）。
値は集まらず、投入の指示が繰り返された。**新しいほうを採る。**

#### 無い値を作らずに入れた

```
旧 youth_candidates 61 件 → 人 61 件 ・ 応募 34 件

  55 件  名        … 氏名に区切りが無い。**姓に氏名まるごと**を入れ、名は空
  61 件  生年月日  … NULL のまま
  31 件  メール    … NULL のまま
  13 件  学校      … 「学校未記録」（非活性）へ寄せる
  27 件  応募日    … 無いので**応募を作らない**（人だけ入れる）
```

**1つも埋めていない。** 埋めれば、その人について嘘の事実が増える。
欠けていることは画面に「未記入」として出る。

#### 学校だけ扱いを変えた理由

`school_id` を NULL 可にすると、**9箇所の内部結合でその人が一覧から
黙って消える。** 消えるのは、無いと書くより悪い。
「学校未記録」という非活性の行へ寄せた（原則3）。非活性なので選択肢には出ない。

#### ★ 踏んだもの3つ

**① 取り込み先を間違えた。**
`.pgdata`（手元の砂場）へ入れてしまい、そこには**創作のデモ 1438 人**が
入っていた。実在と創作の同居は C-28 が禁じている。
引き上げて、本番（`DATABASE_URL`）へ入れ直した。
アプリが読むのも本番のほうである（`src/db/server.ts`）。

以後、書き込み先を毎回名乗るようにした ――
`書き込み先: DATABASE_URL（本番）` / `書き込み先: .pgdata（手元の砂場）`。

**② 開発サーバの検査が、本番への投入まで止めていた。**
PGlite の dataDir 衝突を避けるための検査で、本番接続では起きない衝突である。
`DATABASE_URL` があるときは検査しないようにした。

**③ 識別した日を「いま」で埋めていた。**
年度の母集団は「選考終了日までに識別されたか」で決まる。取り込んだ時刻を
入れたので、**61人全員が2期の外へ落ち、2期の一覧に1人も出なかった。**
旧システムの `created_at`（＝識別した日）をそのまま使うようにして直した。

```
直す前  2期 0 人   3期 61 人
直した後 2期 53 人（応募 34 ・ 未応募 19）
```

#### いま画面に出るもの・出ないもの

```
出る    人を探す（61人）・ファネル（2期の応募 34）・応募の経緯
出ない  ヘッドハンティング／ボーダーラインの一覧
```

出ない理由は1つ ―― これらは `v_headhunting_list`、つまり
**アプローチ状態の記録がある人**だけを出す。取り込んだ61人には無い。

記録するには `approach_events.recorded_by_staff_id`（＝職員）が要るが、
**本番に職員が1人も登録されていない。**
旧データの担当者名を職員として取り込むかは受領していないので、**作っていない。**

#### 冪等

2回流しても増えない。人は `persons.source_ref`（0023 で追加）、
応募は `applications.form_response_id`。実際に2回流して確かめた。
