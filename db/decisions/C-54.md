#### ★ このシードの日付は4つとも受領していない

`seasons` の4つの日付は NOT NULL で、行を作るには何かを入れるしかない。
`CLAUDE.md` の「記録にない値の創作」に触れる以上、
**由来を消さないことを条件に置いた。** 0002（2026年度）で応募締切を
推測で置いたときと同じ扱いである。

推測の根拠は1つだけ ――**2期の周期をそのまま1年ずらした。**

```
2期(2026)  集客 02-01 / 応募開始 03-10 / 応募締切 03-22 / 選考終了 04-15
3期(2027)  集客 02-01 / 応募開始 03-10 / 応募締切 03-22 / 選考終了 04-15
```

**周期が変わらないという保証はどこにも無い。**
実際の日程が分かったら `season_revisions` に履歴を残して直す（原則4）。

#### 入れなかったもの

| | 理由 |
|---|---|
| 定員・目標応募数 | 未受領。**前期の 36 / 100 を今期の数字として写さない** |
| 選考ステップ・評価軸 | 未受領。写すと、変わっていた場合に**運営が使っていない軸**がマスタとして固定化する（原則3） |

#### 期の番号は、マイグレーションとシードの両方が要る

`cohort_number` は 0021 の `UPDATE` で 2026 に 2 を入れていたが、
**新しく作る DB ではマイグレーションがシードより先に走るので、
更新する行がまだ無い。** テストが `cohort_number = 2` を引けずに落ちて
気づいた。0002 のシード自体にも 2 を持たせた。
**既存の本番行にはマイグレーション、新しい DB にはシード。両方要る。**

#### 期が2つになって、テストが22件落ちた

「年度は1件」を前提にしていた箇所が各所にあった
（`SELECT id FROM seasons` を `one()` で受ける形）。
3期は選考ステップも軸も持たない「これからの募集」なので、
選考の検証は**2期に名指しで絞る**形へ直した。
**「1件しかない」を前提にしない。**
