### C-41. 確度スコア（実装段階[3]）に着手した ―― エンジンは作り、規則は作らない

実行⑨。画像の「候補者確度ランキング（96% / 93% / …）」は記録層に無い。
`CLAUDE.md` は「先の段階の機能を勝手に始めない」と定めているので、
**依頼者の判断（「記録層から作る」）を根拠に着手した。**

原典にはスコアリング層のテーブルが4つ（`scoring_rule_sets` /
`scoring_rules` / `score_snapshots` / `score_snapshot_details`）
すでに定義されている。**新しい表は1つも作っていない。**
足したのは、それを動かす集計とビューである（`0017_candidate_confidence.sql`）。

#### 作ったもの／作らなかったもの

| | |
|---|---|
| 作った | 規則を評価して点に畳むエンジン、凍結、順位、順位の変動 |
| **作らなかった** | **規則そのもの（どの事実に何点を付けるか）** |

点数と閾値は原典が「運用時に決定」と書いた値で、依頼者から受け取っていない。
**本番シードには規則を1件も入れていない。** 集計マスタを空で出荷するのは
既存の運用と同じで（最初に入れた値が事実上の初期値として固定化するのを
避けるため）、デモにだけ仮の規則を置いた。

規則が0件なら確度は算出されず、画面は「規則未登録」と出る。**0% ではない。
無いことを 0 と書くと、それは嘘の数字になる。**

#### `target_key` の語彙は構造として閉じた

原典は `target_key` を「運用時に決定」とだけ書いていたが、
何を指せるかが決まっていないと規則を1件も書けない。
**参照できる事実の一覧は構造の問題**なので、`v_scoring_facts` の列に
限る CHECK を足した。点数（値の判断）は依頼者、語彙（構造）はこちら、
という切り分けである。

理由は綴り違いである。`'has_referal'` と書いた規則は、制約が無ければ
**エラーにならず、黙って0点として評価される。**「エラーにならず、
黙って点が減る」は最も気づけない壊れ方なので、書けない形を閉じた。
同じ理由で、比較演算子と条件種別の未知の綴りは0点ではなく例外にしてある。

#### 接点の年度帰属は `v_touchpoint_season` を通す（自前で窓を書かない）

最初 `BETWEEN s.outreach_start_date AND s.selection_end_date` を
自分で書いていた。しかし年度は期間が重なりうるので、その書き方だと
重なる期間の接点が**両方の年度に入る。**
`v_touchpoint_season` は `enrollment_year` の小さいほうへ寄せている。
実行③で踏んだ「同じ言葉が2つの定義を持つ」の再演になるので、正典を通した。

#### 母集団は「算出日時点のヘッドハンティング対象者」に限った

最初は全員（デモで2750人）を凍結していた。結果、候補者の順位が
11位・34位・44位…という通し番号になり、**「候補者の中で何位か」を
答えない一覧**になった。順位は母集団を書かないと意味が決まらないので、
母集団を `compute_score_snapshots` の中で固定し、画面には注記として出す。
**画面側で絞り直させない**（絞り直すと順位と母集団が食い違う）。

#### 順位の変動には算出が2回要る

`score_snapshots` の `calculated_on` が2つ無いと差が出ない。
だから内訳を出す関数は基準日を引数に取る（`jst_today()` で固定しない）。
**「変動なし」と「前回が無い」を別の表示にしてある**（`has_previous_run`）。
前回が無いのに「—」と出すと、動かなかったように読める。
