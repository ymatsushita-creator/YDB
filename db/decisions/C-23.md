### C-23. やることの種別を、4本の枝から1つの優先順位に組み替えた（0014）

実行⑥のレトロスペクティブ（`REPORT-6.5.md`）から出た、必要最小限の設計更新。

0012 の `v_open_tasks` は `UNION ALL` で4枝を並べ、
**「1つの評価は1件のやることにしか出ない」を、枝ごとの除外条件を人が
正しく書き続けることで保っていた。** 保たれなかった（A-18）。

枝が4つ、状態が2つ（pending / held）、相反が2通り。
**組み合わせは種別ごとに読んでも抜ける。** 「評価する」の入力を足せば
状態がさらに増え、同じ穴がまた開く。

そこで枝を1本にし、種別を優先順位で決めた。

```
1. reassign … 利益相反がある（替えるまで、ほかは意味を持たない）
2. unhold   … 保留（解くまで判断は進まない）
3. assign   … 担当がいない
4. evaluate … 担当がいて、判断待ち
```

**1評価=1行が構造になった。** 人が守る規律ではなくなった。
個別の異常を潰すより異常が生まれる余地を閉じる、という 0003 と同じ判断である。

値は 0013 と同じで、列も型も並びも変えていないため
`CREATE OR REPLACE VIEW` で置き換えた（依存する
`v_forest_season_activity` を作り直す必要が無い）。

`process.md` の Refactoring Policy に沿う ――「operational feedback indicates
a problem」のときだけ組み替える。**きれいだからではなく、A-18 が実際に
起きたからである。** ほかに気になる箇所（`v_person_season_state` の直積、
`/people` の応答）は問題が起きていないので触っていない。

**相反の畳み込みについて。** `v_conflict_of_interest` は `UNION ALL` なので
1つの評価に2行つく形がありうる（紹介者かつ本人）。`LEFT JOIN` でそのまま
繋ぐと、1本にした枝がそこで2行に増える。

**いまその形は作れない。** 両方が立つには
`referrer_person_id = person_id` が要るが `persons_no_self_referral` が拒否する。
それでも `DISTINCT ON` で畳んでいるのは、**増えたときに静かに壊れる**
からである。件数が倍になるだけでエラーにならない ―― A-18 で踏んだ
壊れ方そのものなので、制約に頼らず定義側で閉じた。
