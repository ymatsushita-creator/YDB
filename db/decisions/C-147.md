### C-147. 読み込みが遅いのは DB ではなく**距離**だった

依頼者の問い（実行⑮）――「DBどうしたら軽くできんの？」「どうすれば読み込みが早くなるの」。

まず本番の帳簿に読み取り専用で聞いた。**DB は軽い。**

```
DB 全体            15 MB（業務テーブルの合計は約 3 MB）
一番大きい表        persons 672 kB / 512 行
顔写真             9 枚・計 361 kB
一番遅いアプリの SQL  dashboard.ts の季節 CTE 平均 23 ms
```

`pg_stat_statements` の上位を占める 500 ms 級は、すべて Supabase 管理画面や
接続時のカタログ照会（`pg_timezone_names` など）で、**アプリの問い合わせではない。**
索引も `n_dead_tup` も、この母数では触る意味がない。

★ **「重い」を DB の中で探している限り、答えは出なかった。** 出口は外にあった。

#### 見つけたもの ―― 太平洋を往復していた

```
x-vercel-id: hnd1::iad1::…      東京で受けて、**バージニアで実行**していた
DATABASE_URL                    aws-0-ap-northeast-1（**東京**）
vercel.json                     無い ＝ 既定の iad1
```

問い合わせ1回ごとに太平洋を往復する。DB に一度も触らない `/login` ですら、
温まった状態で TTFB 0.33〜0.40 秒だった。

#### 直したもの

```
vercel.json         regions: ["hnd1"]  ―― DB と同じ地域で動かす
src/db/postgres.ts  max: 1 → 3
```

`max: 1` は Supabase session pooler の上限を守るための値だったが、
**それは画面の `Promise.all` を直列に戻していた。** 各ページは問い合わせを
5〜6 本まとめて投げる作りである。本番 DB への実測（手元から・往復 18 ms）――

```
6 往復を Promise.all    接続 1 本 114 ms  →  接続 3〜4 本 50 ms
/people 1 枚分          接続 1 本 134 ms  →  接続 3〜4 本 99 ms
```

往復 170 ms の本番では、この差はそのまま何倍にもなる。3 本にする理由は
「速いから」ではなく、**画面が並列に投げているという事実に接続の側を合わせるため**。

#### デプロイ後の実測（`/login`）

```
x-vercel-id   hnd1::iad1::…  →  hnd1::hnd1::…    受けも実行も東京になった
TTFB（温）     0.334〜0.422 s →  0.183〜0.274 s   平均 0.375 → 0.214 s（約4割減）
初回（冷）      1.85 s        →  0.99 s
```

★ **これは DB に一度も触らないページの数字である。** 縮んだのは利用者↔サーバの
距離だけで、**DB 往復の短縮は1 ms も含まれていない。**

#### ★ 見積もりを、見積もりだと書く

合言葉の要る画面は本番で計っていない（`/login` だけが外から計れる）。
「`/people` の待ちが 0.8 秒前後」も、`max: 3` の効き方も、
**往復回数 × 実測 RTT からの見積もりであって、実測ではない。**
外から測れないものを測れたことにしない。

#### なぜテストに固定するか

どちらも**設定を1行変えるだけで黙って戻る**値で、戻ったことは画面にも出力にも
出ない。C-124 でデプロイ先を固定したのと同じ理由で、期待する側を置く。
