### C-132. ★ 置いた順が現在に出ていなかった ―― 同着すると **id（乱数）で決まる**

C-131 のテストが**ときどき落ちた**（「見送りを置いたのに、現在が
アプローチ中のまま」）。原因は打ち消しではなく、**状態の並べ方**だった。

```
v_person_approach_state          ORDER BY occurred_at DESC, created_at DESC, id DESC
v_partner_recommendation_state   同じ
```

`occurred_at` も `created_at` も `now()` である。**時計が刻めないほど速く
2件入ると両方が同着し、残る手掛かりは `id`（`gen_random_uuid()`）だけ**になる。
つまり **あとから置いたほうが負けることがある。**

測った ―― 同じ瞬間の2行を入れると、**2件目に書いた「対象外」ではなく
1件目の「メール送信済み」が現在**として出た。PGlite の時計はミリ秒刻みで、
続けて打てば普通に同着する（本番の PostgreSQL はマイクロ秒だが、
**取り込みのように機械が続けて書けば同じことが起きる**）。

★ 0035 のコメントは「同じ瞬間に2件入った場合は created_at、それも同じなら
id で決める」と書いていた。**決まってはいる**（同じデータなら同じ答えが出る）。
決まっていなかったのは**それが置いた順だという保証**のほうである。

#### 直したもの

新しい出来事の `occurred_at` を、**同じ相手・同じ期の直前の出来事より
必ず後ろ**に置く ――

```sql
greatest(now(), (SELECT max(occurred_at) + interval '1 microsecond' FROM … ))
```

★ `greatest` は NULL を無視するので、1件目はそのまま `now()` になる。
★ ずらす幅は**1マイクロ秒**。「いつ起きたか」を歪めない最小の幅である。
★ ビューは触っていない。**並べ方ではなく、置き方を直した** ――
  ビューに手を入れると、取り込みが入れた過去日付の行の意味まで変わる。

★ これは**打ち消しにとっては必須**である。打ち消し行が同着で負けると、
**訂正したのに元の値が現在のまま**になる。C-131 の道は、この保証の上に立つ。
