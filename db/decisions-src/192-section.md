### C-141. 画面の切り替えが遅い理由を測った ―― **SQL は遅くない**

依頼者の問い（実行⑮）――「**画面切り替えはなぜこんなに遅いの**」。

推測で答えず、測った。

```
本番 /login の応答        0.39〜0.72 秒 ―― **DB に触らない画面でこれ**
デモDBの組み立て          1,244 ms
  PGlite 起動(WASM)        621 ms
  migrate（0001〜0037）     99 ms
  seed（参照＋例）            2 ms
  seedDemo（架空データ）     522 ms
画面ごとの問い合わせ        10本ぜんぶ足して 219 ms
  ホーム推移 64 ／ 特別選考の一覧 34 ／ 通常選考の確度順 91（ms）
```

★ **遅いのは問い合わせではない。** 遅いのは3つ ――

```
① 本番はデモモード（C-94）で、インスタンスが立つたびに DB を丸ごと組み立て直す
   ―― アクセスが途切れて入れ替わるたび、**次の1人が 1.2 秒以上を払う**
② 19画面すべて force-dynamic。押すたびにサーバへ往復する
③ `loading.tsx` が1枚も無い。応答が返るまで**画面は前のまま**で、
   押した手応えが無い。同じ 0.5 秒でも体感は倍以上になる
```

#### 入れたもの ―― ②への手当て（ブラウザ側の控え）

```
next.config.ts   experimental.staleTimes = { dynamic: 30 }
```

タブを押し直したとき、30秒はブラウザの控えを使って**押した瞬間に出す。**

★ **書き込みのあとに古い値を見せない。** 記録を書くアクションはすべて
`revalidatePath()` を呼んでおり、それが控えごと捨てる（`tests/45` で全数を固定した）。
**読むだけの往復を減らす指定であって、書いた結果を古くする指定ではない。**

★ 30秒より長くしない ―― 運営は2人以上で同じ期を触る。隣の人が入れた値が
出るまでの待ちが、そのまま長くなる。

#### 測っただけで、まだ入れていないもの

```
                              **`pglite.dumpDataDir()` で作れることは確認した**
C  loading.tsx                骨組みの見た目は依頼者の指示待ち
D  本番を実DBに向ける          組み立てが丸ごと消える。ただし①認証 →②戻し方 →
                              ③DB分離が先（C-84 / C-94）。**Dをやると B は要らなくなる**
```
