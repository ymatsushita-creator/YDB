## C-220 設計判断を1件ずつ開ける形にした（封印を書き換えずに）

依頼者の指示 ――「ディレクトリ構成をAI開発に最適な状態にしろ」。
4セッションにわたって出ていた指示で、そのあいだ**実行されていなかった。**

#### 何が本当の障害だったか

構成診断（`.consultant/DIAGNOSIS.md`）は本題をこう書いていた ――

```
db/DECISIONS.md   496,136字 ≒ 33万トークン相当
→ どの文脈長にも入らない。AIはこの「なぜ」の層を読めない。
```

読めない層は参照されず、参照されない層は更新されない。
**欠番45件（実行⑯・⑰の判断が1件も記録されずに終わったこと）は、この構造の結果である。**

対処として `pnpm decisions:show` を置いてあった。だがこれは**端末を持つ相手にしか効かない。**
AIが最初にやるのは grep とファイルを開くことで、コマンドの存在を知らなければ
49万字を開こうとする。**道具ではなく、ファイルの側を開ける形にする必要があった。**

根治は分割だが、`CLAUDE.md`（封印下）が `db/DECISIONS.md` を「設計判断の本体」と
名指ししている。分割には憲法の書き換えと再封印（＝人間が端末で合言葉を打つ操作）が要る
―― そう記録して、**4回にわたり「人間の判断」として持ち回っていた。**

#### 封印を書き換えずに済む形があった

★★ **正典は動かさない。写しを増やす。** ★★

```
db/DECISIONS.md        496.1KB  正典。CLAUDE.md が名指しする「本体」。**開かない**
db/decisions/C-176.md    2.0KB  ← AIも人も、開くのはここ
db/decisions/README.md          217件の目次
```

`db/decisions/` は **生成物**（`app/tokens.css` / `db/DECISIONS-INDEX.md` と同じ扱い）。
`CLAUDE.md` の記述は1字も変わらない ―― 本体は本体のままで、
記録を足すのも本体へ。**封印の解除は要らなかった。**

★ `MANIFEST.sha256` を確認した。`db/DECISIONS.md` は封印対象では**ない**
  （封印されているのは `CLAUDE.md` / `AGENTS.md` / `process.md` / `domain.md` /
  `director.md` / `SUPERVISOR.md` と監査基盤）。分割そのものは前から可能だった。
  **障害は封印ではなく、封印を理由にしていたことである。**

#### 決めたこと

★ **1件1ファイル。** 番号がファイル名になる（`C-176` → `db/decisions/C-176.md`）。
  grep でも当たり、ファイル名から番号が引ける。最大 12KB（C-217）。
★ **本文は一字一句そのまま写す。** 要約しない ―― 要約した写しは、
  読んだ人が原文を読まなくなるので、原文より危ない。
★ **重複した番号は1つのファイルに両方載せ、先頭で競合を告げる**（`C-45` / `C-46` / `C-116`）。
  黙って片方を捨てない。振り直しは生成側では行わない
  ―― 番号はコミットメッセージからも参照され、git 履歴は後から直せない。
★ **節（`## F. 実行環境について`）は写しに書かない。** 本体は 1941行目以降が
  すべて F 節の中に在り、C 番号の記録まで F に属して見える。分類は接頭辞が持つ。
★ **作り直しは消してから書く。** 番号を消したのに写しが残ると、
  本体に無い参照先が開ける状態になり、**索引より写しのほうが新しく見える。**
★ **写しは参照元の照合から外す**（`decisions-refs.ts` の `EXCLUDE`）。
  外さないと、欠番の参照元が本体と写しで二重に並ぶ。
★ 大きさを検査する（1件 20KB 上限）。**分割の目的は「開ける大きさにする」ことで、
  大きさを見張らないと目的が形骸化する。**

#### 併せて塞いだ穴

`pnpm decisions:show` は本文の終わりを「次の番号の見出し」だけで決めていたので、
**節の最後の記録が次の節見出しまで飲み込んでいた。**
切り出しを `decisions-refs.ts` の `sliceEntry` に寄せ、節見出しでも止める。
写しと `decisions:show` が同じ関数を通るので、以後ずれない。

#### 導線

作った道具が着手導線から見つからない失敗（`.consultant/DIAGNOSIS.md` 所見7）を
繰り返さないため、`README.md`・`HANDOFF.md`・`.claude/commands/decisions.md`・
`.claude/agents/investigator.md`・`.claude/commands/plan.md` に「まず
`db/decisions/<番号>.md` を開く」と書いた。

検証: `tests/82_decisions_parts.test.ts` 6件（本体と写しが1対1／本文が一字一句同じ／
すべての写しが生成物と名乗る／1件が 20KB に収まる／重複番号は競合を告げる／目次から辿れる）。
CI（`quality.yml`）が `pnpm decisions:parts -- --check` でずれを落とす。
`pnpm verify` にも入れた。
