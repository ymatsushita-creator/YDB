### C-225. `setPersonApproachState` が必ず例外で落ちていた

> ★ **旧番号 C-46。** 同じ番号が2件の判断に使われていたため、2026-08-19 に
> **後から書かれたこちら**へ新番号を振った（C-227）。
> `C-46` を指す参照は、**前者（候補者プロフィールは現在値と追記履歴を同時に保存する）と
> 本項のどちらかを指す。**

実行⑨。**アプローチ状態の編集は、画面からもテストからも一度も成功していなかった。**

```js
[...].every(UUID.test)      // ← this を失って TypeError
```

`UUID.test` をメソッドのまま渡していたため、`this` が `undefined` になり
「incompatible receiver」で必ず落ちる。**入力を検証するつもりの行が、
検証ではなく事故そのものになっていた。**

同時に、この経路を守るはずの `tests/29_profile_editing.test.ts` も
落ちていた ―― マイグレーション 0016 が使う `sort_order = 10` と
同じ値でマスタを追加しており、UNIQUE 制約に当たっていた。
**テストが先に落ちていたので、その奥の本当の欠陥が隠れていた。**

- 検証は `(v) => UUID.test(v)` に直した
- テストは既存の並び順とぶつからない `sort_order = 15` に直した
  （マスタは「追加と非活性化で運用する」ので、追加自体は正しい）

#### 確かめ方

`tests/29_profile_editing.test.ts`「アプローチ状態の編集は担当者付きイベントとして追記する」。
加えてデモ経路の画面で、候補者の状態を
「面談調整中 → 検討中」に変更し、対象者一覧の表示が追随することを
DOM の値で確認した。
