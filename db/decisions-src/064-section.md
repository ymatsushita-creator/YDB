### C-20. 初めての書き込みを、クライアント境界を作らずに足した

実行⑥（`REPORT-6.2.md`）。`/cockpit` から「担当を決める」を実行できるようにした。
それまで画面はすべて読み取り専用で、**記録を変える経路が1本も無かった。**

**着手前に確かめたこと。** `HANDOFF.md` は「クライアント側のライブラリを
採用するのはクライアント境界を新設する判断と同義なので、その判断は単独で示す」と
定めている。書き込みがそれに当たるかを先に確認した。

**当たらない。** サーバアクションを素の `<form action={...}>` に渡す形は、
サーバコンポーネントの中に置ける。`'use client'` は0件のままで、
**JavaScript を無効にしても動く。** `'use server'` は「サーバで動く関数」の
宣言であって、`'use client'` の対ではない。
状態を持つ対話部品（`useActionState` など）を入れる段になったら、
そこで初めて境界の判断が要る。

置き場所を3つに分けた。**判定を、テストできる場所に置くため**である。

| 層 | 置き場所 | 役目 |
|---|---|---|
| 判定と更新 | `src/commands/assign.ts` | 事実を確かめて1列だけ更新する。**テストから直接呼べる** |
| 受け渡し | `app/cockpit/actions.ts` | フォームの値を渡し、結果コードを付けて戻す |
| 表示 | `app/cockpit/page.tsx` | `<form>` と結果の通知 |

サーバアクションは Next の実行時が要るためテストから呼べない。
**判定をそこに書くと、いちばん壊れると困る部分がテストの外に出る。**

`src/queries/` に混ぜなかった理由は、守るべき規律が違うことである。
読み取りは母集団を間違えても数字がずれるだけだが、書き込みは記録を壊す。

**操作できる母集団を、画面と同じ述語に揃えた。** 更新対象は
`v_open_tasks` の `'assign'` に出ている評価だけで、`evaluations` 直結にしない。
直結すると、画面に出ていない評価（終わった応募、個人情報削除を受けた人のもの）を
`evaluation_id` の直打ちで触れてしまう。フォームの hidden は誰でも書き換えられる。

**UPDATE は条件付きにした**（`WHERE state = 'pending' AND
interviewer_staff_id IS NULL`）。確認と更新の間に誰かが割り当てても、
0 行更新で終わり、後から来たほうが黙って上書きしない。

**結果は URL のコードで返す**（PRG）。`?assign=ok` のように**コードだけ**を渡し、
氏名や応募の id は渡さない。URL は履歴にもログにも残るので、
個人が分かる値を置く場所ではない。誰を誰に割り当てたかは、戻った画面を見れば分かる。

**残したもの。** 誰がいつ割り当てたかは記録されない。`evaluations` に担当の
変更履歴を持つ列が無く、原典にも無い。`status_histories` は応募の遷移の記録で、
担当の付け替えは遷移ではない。**TODO(MVP)**: 運用して「誰が決めたのか
分からない」と困ってから、追記専用の表を1つ足す。
