### C-25. 点と根拠を1軸ずつ保存する（E2）

実行⑥（`REPORT-6.7.md`）。「評価する」の第2段。**初めて記録が増える書き込み**
である（これまでの3つは既存の行の1列を変えるだけだった）。

**1軸1行にした理由。** `evaluation_scores` の一意制約が
`(evaluation_id, criteria_id)` なので、記録層にとって自然な単位が1軸である。
全軸まとめて保存する形にすると、面接の途中で1つだけ書き留められない。

**★ 入力の検証を書き写していない。** 規則はすべて記録層にある ――
根拠の空白禁止（CHECK、0015）、上限の `scale_max` 参照とステップ・再応募の
適用判定（トリガ `evaluation_scores_validity`）。同じ規則をコマンドにも
書くと、片方だけ直したときに食い違う（C-11）。**保存を試みて、失敗を
写して返す。**

写す先は制約名とトリガの文面である。**依存していることを隠さない** ――
変わればテストが落ちるよう、tests/20 で1つずつ実際に踏ませている。
知らない拒否は「保存できた」に丸めず、例外をそのまま投げ直す。

画面の `max` と `required` は**補助**であって判定ではない。実際に
`required` を外して全角スペースを送り、記録層が弾くことを確かめた（A-19）。

**操作できる母集団を、運転席の種別に揃えた。** 点を付けられるのは
`v_open_tasks` の種別が `'evaluate'` のものだけである。担当未割当・保留・
利益相反の評価に点を付けられると、**運転席が出している順序（先に担当を
決める・解く・替える）を素通りできる。** 画面はその理由を名指しする
（「先に担当を決める」など）。「できません」だけでは運用者が止まる。

**上書きしない。** すでに点が付いている軸は `already_scored` で返す。
点の訂正（E4）は別の判断である。スコアは再現不能な値として扱われており
（原則2）、上書きの規則を決めずに通せる場所ではない。

**確定（`submitted`）にはしない。** 全軸そろっても `pending` のままである。
確定は E3 の判断で、そこには「全軸そろう前に確定させない」という別の規則が要る。

運転席には `n/m 軸` を出しているので、**1軸ずつ埋まっていく様子がそのまま
進捗として読める**（面接官が2人いる同じステップも、それぞれ独立に数える）。

→ `tests/20_score.test.ts`「点と根拠が保存され、その軸は「これから付ける軸」から消える」
→ `tests/20_score.test.ts`「1軸ずつ足していける（途中で止めても残る）」
→ `tests/20_score.test.ts`「0 点も保存できる（未入力と区別する）」
→ `tests/20_score.test.ts`「同じ軸に二度は付けられない（訂正は別の判断）」
→ `tests/20_score.test.ts`「満点を超えた点は拒否される（トリガの scale_max 参照）」
→ `tests/20_score.test.ts`「別のステップの軸は付けられない」
→ `tests/20_score.test.ts`「再応募でない応募に、再応募者限定の軸は付けられない」
→ `tests/20_score.test.ts`「担当が決まっていない評価には付けられない」
