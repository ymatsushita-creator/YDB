### A-16. 年度を1つ指定すると、集計が 9000 倍遅くなった ★影響大

実行⑥。0012 で作った `v_forest_season_activity` を画面から呼んだところ、
**開発サーバが応答しなくなった。** CPU を 64% 使い続けており、
止まっているのではなく回り続けていた。

書いた直後に測ってはいた。`SELECT count(*) FROM v_forest_season_activity`
が 19 ミリ秒だったので、速いと判断した。**その測り方が間違っていた。**

| 測り方 | 実測 |
|---|---|
| 全件（`WHERE` なし） | 19 ミリ秒 |
| 年度を1つ指定（リテラル） | 177,694 ミリ秒 |
| 年度を1つ指定（パラメータ） | 176,656 ミリ秒 |

リテラルでもパラメータでも同じなので、プリペアドの汎用プランの話ではない。
**述語のプッシュダウンである。** `season_id = X` が各 CTE の内側へ降りると、
プランナは「対象は数行」と見積もってハッシュ結合をやめ、入れ子ループを選ぶ。
その内側に居るのが `v_open_tasks` と `v_application_state` で、どちらも
`v_effective_status_histories`（再帰 CTE）を通る。**外側の行ごとに再帰が
回り直す。** A-8・A-11 と同じ構図である。

**A-11 と向きが逆である。** あちらは「氏名で絞ると速いので、手元で軽く
触るだけでは気づけない」だった。だから実行③以降「一覧は必ず素の状態
（絞り込みなし）で開いて確かめる」を手順にしていた。今回はその手順
どおりに測って、**絞り込みなしだけが速い**という逆の形を見逃した。
片側だけを測る限り、どちらの向きも取り逃す。**両方で測る。**

**対応**は2つある。どちらも「絞り込みを、高い供給元まで降ろさない」。

1. `v_forest_season_activity` の供給元 CTE（`forest_person` / `countable` /
   `open_tasks`）を `MATERIALIZED` にした。`MATERIALIZED` はプッシュダウンを
   禁じる指定そのもので、供給元を1回ずつ走ってから畳む。
   年度を1つしか見なくても全件を1回走ることになるが、爆発しないほうを取る。
   **177 秒 → 0.15 秒。** 全件は 0.02 秒のままで、桁の差が消えた
2. `v_open_tasks` の `season_id` を、応募（`a.season_id`）ではなく
   選考ステップ（`ss.season_id`）から取るようにした。応募側から取ると
   同じ述語が `v_active_applications` を通って再帰 CTE まで降りる
   （0.074 秒 → 0.413 秒）。ステップ側なら小さな表で止まる（0.074 → 0.076 秒）。
   既存の `getPendingEvaluations` も `ss.season_id` で絞っており、そちらに揃う形でもある

`v_open_tasks` を丸ごと `MATERIALIZED` で押さえる案も測った。絞り込みの
有無によらず 1.05 秒になり、全応募を毎回実体化する分が節約を上回った。
**採らなかった案も測ってから捨てる。**

固定の仕方について。**実行時間はテストに書かない。** データ量とマシンに
依存する数字を残しても追試できないし、閾値は環境が変われば嘘になる
（「作り物のデータから出た数字をドキュメントに残さない」）。
残すのは**プランが崩れない形のほう**なので、ビュー定義そのものを見張る。

→ `tests/15_forest_and_tasks.test.ts`「森×年度の集計は、供給元を1回だけ走る形を保っている」
→ `tests/15_forest_and_tasks.test.ts`「やることの年度は、選考ステップ側から取っている」
→ `tests/15_forest_and_tasks.test.ts`「どちらから取っても、年度の値そのものは変わらない」
