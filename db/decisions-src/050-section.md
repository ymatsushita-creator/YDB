### D-8. 実データの値が未確定（seasons）

2026-08-06 の指示で「`seasons` の年度・定員(36)・目標応募数(100)は実数値」と
伝えられた。ただしそれがどの年度のもので、4つの日付
（`outreach_start_date` / `application_open_date` / `application_close_date` /
`selection_end_date`）がいつなのかを確認できていない。

そのため本番のシードに `seasons` の行は入れていない。
デモの `src/seed/demo.ts` にある4年度（定員 24/30/36/40、目標 150/220/300/340）は
すべて創作で、実数値ではない。

年度と4つの日付が分かった時点で、定員36・目標100の年度を
本番のシードに追加する。

#### 2026-08-07（実行⑦）追記 ―― 入れた。ただし**2列が推測値である**

旧 NEO-Youth の DB とコードから回答を受け、本番のシードに
2026年度・選考ステップ4件・評価の観点6件を入れた。
置き場所は `db/seeds/0002_season_2026.production.sql` で、
**創作のデモが入る環境には入らない**（C-28。入れると創作の応募が
実在の年度にぶら下がる）。
受領の経緯と読み取った内容は `docs/pilot/DATA-QUESTIONS.md`。

**確定と推測を分けて記録する。** 分けずに書くと、あとから読んだ人が
全部を確定として扱う ―― 「記録が実装より厳密に見える」の再発になる。

| 列 | 値 | 由来 |
|---|---|---|
| `enrollment_year` | 2026 | **確定**（全データが2026年） |
| `outreach_start_date` | 2026-02-01 | 1次面談の開始日。**日付は確定、集客起点への充て方は判断** |
| `application_open_date` | 2026-03-10 | **確定**（応募フォームの受付開始） |
| `application_close_date` | 2026-03-22 | **★推測。** 締切は DB にもコードにも無い。実績の最終応募日を締切と見なした |
| `selection_end_date` | 2026-04-15 | 合否通知・入金案内の日。**日付は確定、選考終了への充て方は判断** |
| `capacity` / `target_application_count` | 36 / 100 | **確定**（2026-08-06 受領） |

**推測値をシードに入れるのは `CLAUDE.md` 9節に反する。**
それでも入れているのは、依頼者が推測と明示したうえで置くと決めたためで、
**由来を消さないことを条件にしている。** 実際の締切が判明したら
`season_revisions` に変更履歴を残して直す（原則4）。日付は集計定義そのもので、
黙って上書きすると過去の帰属が動く。

**記録できなかったものが2つある。**

1. **「NEO ACADEMIA 2期生」という名称。** `seasons` は `enrollment_year`
   （整数）しか持たず、名前の列が無い。**期の呼び方が入らない。**
   画面は「2026年度」としか出せない。列を足すかは未決（D-13）
2. **「選考開始 2026-03-23」（推測）。** `seasons` は4つの日付しか持たない。
   応募締切と選考終了の間に選考開始という段は無い

**選考ステップは8つの遷移のうち4つだけを入れた。**
旧システムの遷移は 応募前 → 応募完了 → 書類選考 → グループ面接 → 最終面接
→ 合格予定 → 合格／補欠合格 → 承諾書提出 の8つだが、**このうち段は4つで、
残りは結果か状態である。** 合格を `selection_steps` に入れると
「最終ステップを通過したら合格」（`sort_order` の最大）が壊れる ――
合格そのものが段になるため、通過しても次の段が残りつづける。
`sla_days` と `pass_criteria` は入れていない。**旧システムに記録が無く、
推測で入れると根拠のない日数で SLA 超過が鳴りはじめる。**

**評価の観点は最終面接の6軸のみ。** 各4点満点・合計24点満点で、
**依頼者に確認して確定した。** `evaluation_criteria` は年度ではなく
ステップに属する（`selection_step_id`）ため、6軸は最終面接に付く。
旧 DB では `candidates.sec2_*` に入っていたが、あの表は最終面接シートであり、
`sec2` は旧システムの呼び名にすぎない。

**書類選考の軸は入れていない。** 満点16は確定している（画面に `/16` と
明記されていた）が、旧システムは `doc_score` という数値を1つ持つだけで
**軸の呼び名が無い。** こちらで名付けると、運営が使っていない語が
マスタとして固定化する（原則3、および Pilot Rule「運営の言葉を
こちらの語に翻訳して記録しない」）。グループ面接の軸も無い
（`sec2_group` は A〜E の組分けであって評価ではない）。

**`doc_score` は「実測の最大は満点ではない」の実例である。**
実測13・満点16だった。6軸のほうは実測の最大24が 6×4 と一致したが、
そこから満点を推定していたら `doc_score` で間違えていた。
**満点は確認して得るものであって、データから推定するものではない。**

固定しているテストは `tests/22_reference_season.test.ts`（12件）。
値だけでなく**入れていないこと**も検査する ―― 書類選考とグループ面接に軸が
無いこと、SLA が空であること、結果や状態がステップに混ざっていないこと、
シードが個人を1人も作らないこと。3箇所をわざと壊して7件が落ちることを確認した。
