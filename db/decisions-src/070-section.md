### C-26. 確定と判定 ―― 採用の1周を画面の中で閉じた（E3 / D1）

実行⑥（`REPORT-6.8.md`）。**今日 MVP を完成させる**という指示に対する
最後の2つ。これで Definition of Done の9項目がすべて画面から実行できる。

```
今日やることを見る → 候補者を開く → 担当を決める / 替える / 保留を解く →
評価する（軸ごとに点と根拠）→ **確定する → 判定する → 次のステップへ**
```

**E3 確定。** 全軸そろった評価を `submitted` にする。
**そろう前の確定を認めていない。** 途中で確定できると「点が2つしか無い評価」が
残り、ステップ別の平均が軸によって母数の違う値になる。認めないほうが単純で、
必要だと分かったら緩める（TODO(MVP)）。

**D1 判定。** `status_histories` に1行追記し、通過なら**次のステップの
評価行を作る。担当は付けない。** それが運転席の「担当を決める」として並ぶ ――
**判定の結果が、次の一手として自動で現れる。** 最終ステップの通過は合格で、
何も作らない。

成立条件を3つとも事実で見る（原則7）。

1. 応募が動いている（`v_active_applications`）
2. そのステップの評価がすべて提出済み
3. そのステップの遷移がまだ無い（二重に判定しない）

**面接官が2人いるステップは、2人とも確定してから判定できる。**
実データで確かめた ―― 1人目を確定しても判定の欄は出ず、2人目を確定した
時点で「二次面接 の判定（評価は 2 件すべて確定済み）」が現れた。

**★ 不合格にステップを結び付けた。** `CLAUDE.md` 8節は構造の穴として
「`reject` にステップが結び付いていない。推測で埋めると根拠のない数字が
一人歩きするので、必要になったら持たせる」と書いていた。

**画面から判定する以上、どのステップで落ちたかは推測ではなく事実として
手元にある。** だから埋める。埋めなければ「どのステップで落ちたか」を
永久に集計できない。**ただしデモと過去の記録には入っていない**ので、
集計を作るときは母数がここから先の判定だけであることを注記する必要がある。

**訂正は扱わない。** `status_histories` は追記専用（0003）で、判定の訂正は
打ち消し行の追記でしか表せない（原則5）。画面にも「判定は打ち消しの追記で
しか訂正できない。押す前に確かめる」と出している。
