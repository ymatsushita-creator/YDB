## 1. 点検 ―― 打ち消せる記録は4つ、画面から打ち消せたのは1つ

その打ち消し列（`corrects_*`）を持つ記録を数え上げると4つあり、
**道が画面まで通っていたのは1つだけ**だった（C-129）。

| 記録 | 記録層 | コマンド | 画面 |

| `status_histories`（0001） | ある | `correctDecision` | ある |
| `approach_events`（0016） | ある | ★無い | ★無い |
| `person_notes`（0027） | ある | ★受け口だけ | ★無い |
| `partner_recommendation_events`（0035） | ある | ★無い | ★無い |

★ `person_notes` は**コマンドが `correctsNoteId` を受け取れるのに、
渡していたのはテストだけ**だった。形はあったが、運用者から見れば無いのと同じ。

★ **規律に書いてあることが、画面でできないままだった。** 記録層の欠陥ではなく、
**道の欠陥**である。

## 2. 先に塞いだ穴 ―― 打ち消しが**別の相手**の記録を消せた（C-130）

数えた4つのうち、**打ち消せる相手を縛っていたのも `status_histories` だけ**
だった（0007）。残る3つでは、こうなる ――

```
乙さんの行から**甲さんのメモ**を打ち消せる
Y大学の行から**X大学の推薦枠**を打ち消せる
3期の行から**2期の記録**を打ち消せる
```

打ち消された行は `v_effective_*` から**黙って落ちる。** 消された側の画面には
何も出ない ―― 0007 が `status_histories` について書いた壊れ方が、
**あとから足した3つで開いたままだった**（訂正チェーンの再帰判定は写したのに、
範囲の縛りは写されていなかった）。

★ **入口を開ける前に閉じた。** SQL でしか書けないあいだ、この穴は運用の手が
届かない場所にあった。画面から打ち消せるようにすれば、取り違えは
**普通の操作として**起こりうる。順番を逆にしない。

判定は**書き写さず**、列を引数で渡す1つの関数にした（0036
`check_correction_scope_of`）。C-126 と同じ理由である。

## 3. 通した道（C-131）

打ち消し行の形は `correctDecision` にそろえた ―― **打ち消し行が正しい値を
載せて元に取って代わる。** 元の行は記録層に残り、有効判定のビューから落ちるだけ。

```
メモ            /borderline のメモ ―― 各メモに「取り消す」を畳んで置いた。
                取り消す人と理由は記入必須で、**打ち消し行の本文が
                「なぜ取り消したか」として一覧に残る**
アプローチ状態   /people/{id}/edit ―― 欄は同じで、**押すボタンで意味が変わる**
                「状態を記録」＝積む／「直前を訂正」＝打ち消して置く
推薦枠ステイタス /reach-zones/{id} ―― **置くのは表、直すのは団体の頁**
```

★ **なぜ置き直しでは足りないか** ―― 0035 のテストが書いたとおり、出来事を
積むことには「**その日に動きがあった**」という意味がある。打ち間違いを
置き直しで直すと、動いていない日が動いたことになる。

★ **終端の状態を押し間違えたら戻れなかった。** 見送りと対象外は
「これ以上こちらから動かさない」状態で、訂正の道が無いと、その人・その団体は
**一覧に二度と現れない。**

★ 打ち消す相手は**コマンドが記録層から引く。** 画面から出来事の ID を
渡させると、古い画面を開いたまま押したときに**見ていない行を打ち消せる。**

## 4. 掘っている途中で出た欠陥 ―― 置いた順が現在に出ていなかった（C-132）

C-131 のテストが**ときどき落ちた**。原因は打ち消しではなく、**状態の並べ方**。

```
ORDER BY occurred_at DESC, created_at DESC, id DESC
```

`occurred_at` も `created_at` も `now()` である。**時計が刻めないほど速く2件
入ると両方が同着し、残る手掛かりは `id`（乱数）だけ**になる。
つまり**あとから置いたほうが負けることがある。**

測った ―― 同じ瞬間の2行を入れると、2件目に書いた「対象外」ではなく
**1件目の「メール送信済み」が現在**として出た。

直したのは**並べ方ではなく置き方**である。新しい出来事を、同じ相手・同じ期の
直前の出来事より**必ず1マイクロ秒後ろ**に置く。ビューに手を入れると、
取り込みが入れた過去日付の行の意味まで変わる。

★ これは**打ち消しにとって必須**である。打ち消し行が同着で負けると、
**訂正したのに元の値が現在のまま**になる。

## 5. 点の訂正（E4）―― 直せるのは未確定の評価だけ（C-133）

C-25 が保留していた最後の1つ。規則の選び方は依頼者から委ねられ（問いへの
答えは「特に無い」）、**狭いほうを選んだ。**

```
直せる    未確定（pending）。担当が決まっていて、判断がまだ下りていない
直せない  確定（submitted）した評価の点
```

★ 確定は**判断の材料が締め切られた印**である。あとから点が動くと、確定時に
見ていた数字と今の数字が食い違い、**合否の根拠が後から書き換わる。**
確定を戻す道は別にある（判定の訂正・保留）。そちらを先に通ってもらう。

★ **広いほうは要ると分かってから足せる。逆はできない** ―― いったん通した
上書きをあとから狭めても、通っているあいだに書かれた行は残る。

```
記録層   0037 evaluation_score_revisions（追記専用。版には**変更後**の値）
コマンド correctScore ―― 保存と**別の入口**。同じ入口が「無ければ入れる・
         あれば直す」を兼ねると、**二度押しが訂正として通り、版だけが積まれる**
門       saveScore と**同じもの**（v_open_tasks の 'evaluate'）を見る
画面     採点シート（2画面）と応募の画面に「直す」を畳んで置く。確定前だけ
```

★ 上書きと版は**1つの取引**。満点超えを試すと**現在値も版も動かない**
ことをテストで踏ませている。

★ **直した人は残さない。** 認証が無く、名簿を選ばせても自己申告にしかならない
（C-84 / C-85）。メモの「書いた人」は依頼者の指示で必須にしたが、点の
打ち直しに同じ指示は受けていない。**受けていない指示を先回りで作らない。**
