## 2. 得られた知見（実装からしか出なかったもの）

### 2-1. 性能は「絞り込みあり」と「なし」の両方で測る

A-16。全件 19 ミリ秒の集計が、**年度を1つ指定した瞬間に 177 秒**になった。
述語が CTE の内側へ降り、再帰 CTE が外側の行ごとに回り直していた。

**A-11 と向きが逆だった。** あちらは絞ると速くなって見逃した。だから実行③以降
「一覧は絞り込みなしで開いて確かめる」を手順にしていた。**その手順どおりに
測って見逃した。** 片側だけでは、どちらかの向きを必ず取り逃す。

### 2-2. 種別ごとに条件を足す設計は、組み合わせの数だけ穴が開く

A-18。「やること」4種のうち `evaluate` から利益相反を除いたのに、`unhold` に
付け忘れて二重計上になった。枝4 × 状態2 × 相反2 を**種別ごとに読んでも抜ける。**

**これが今回の設計更新の理由になった**（4節）。

### 2-3. 制約は、書いた本人が読み直さないと効かない

C-21。「保留を解くと必須の理由が消える」と判断し、**指示を仰いで止まった。**
制約は `CHECK (state <> 'held' OR hold_reason IS NOT NULL)` で、
「保留でなければ持てない」ではなかった。**1行読み直せば消える問いだった。**

A-17 も同種である。`LEFT JOIN ... AND p.deleted_at IS NULL` と書いて、
外部結合が行を落とさないことを忘れていた。**1文字も効いていなかった。**

### 2-4. 誤った前提は、判断を過剰に保守的にする

F-1。「クライアント JavaScript を一切配信していない」という記録が誤りだった。
その前提で考えると、フォームの送信すらクライアント境界の新設に見える。
**実際には素の `<form action={...}>` で足り、`'use client'` は0件のままだった。**
記録の誤りは、機能を足せなくする方向にも働く。

### 2-5. 組み合わせを1つ置き忘れると、分岐は静かに死ぬ

C-19 と A-18。デモに「保留かつ利益相反」が無かったため、二重計上は
表に出なかった。`reassign` そのものも一度も踏まれておらず、**対になっている
除外条件も同時に死んでいた。** 「デモが経路を踏んでいない」は**5回目**である。

## 3. 何が誤りだったと分かったか

| 置いていた前提 | 実際 |
|---|---|
| 絞り込みなしで測れば性能は分かる | 絞ると 9000 倍遅くなる形がある（A-16） |
| 種別ごとに条件を確かめれば足りる | 組み合わせは種別ごとに読んでも抜ける（A-18） |
| 保留を解くと理由が消える | 消えない。制約を読み違えていた（C-21） |
| クライアント JS を配信していない | 配信している。境界の判断が過剰だった（F-1） |
| `LEFT JOIN` の `ON` で絞り込める | 行は落ちない（A-17） |

**5つのうち4つは、記録層かフレームワークを読めば実装前に分かった。**
残る1つ（A-16）だけが、動かさなければ分からなかった。

## 4. 必要最小限の設計更新（0014）

**やることの種別を、4本の枝から1つの優先順位に組み替えた。**

0012 は `UNION ALL` で4枝を並べ、「1つの評価は1件のやることにしか出ない」を
**枝ごとの除外条件を人が正しく書き続けること**で保っていた。保たれなかった
（A-18）。「評価する」の入力を足せば状態がさらに増え、同じ穴がまた開く。

```
1. reassign … 利益相反がある（替えるまで、ほかは意味を持たない）
2. unhold   … 保留（解くまで判断は進まない）
3. assign   … 担当がいない
4. evaluate … 担当がいて、判断待ち
```

枝を1本にし、種別を `CASE` で決める。**1評価=1行が構造になった**（人が守る
規律ではなくなった）。値は 0013 と同じで、列も型も変わらないため
`CREATE OR REPLACE VIEW` で置き換えた。

これは `process.md` の Refactoring Policy に沿う ――
「Refactor only when … operational feedback indicates a problem」。
A-18 が実際に起きたのが根拠である。**きれいだからではない。**

**更新はこれだけにした。** ほかに気になる箇所（`v_person_season_state` の
直積、`/people` の 1.4 秒）はあるが、**問題が起きていないので触らない。**

## 5. 「評価する」の分割

指示に従い、大機能としてではなく**1サイクルで終わる単位**に割った。

「評価する」が重い理由は4つある。

- 更新が1列でない（`evaluations` と `evaluation_scores` の両方）
- `rationale` が必須で、**軸ごとに**テキスト入力が要る
- 再応募者限定の軸があり、応募によって入力欄の数が変わる
- スコアは凍結対象（原則2）。取り消しの扱いが上書きより重い

`evaluation_scores` の一意制約が `(evaluation_id, criteria_id)` である。
つまり**1軸ずつ保存する操作を、スキーマが最初から許している。**
ここが分割線になる。

| # | 単位 | 書き込み | 独立して使えるか |
|---|---|---|---|
| **E1** | **評価すべき軸を見せる**（点・根拠・未入力を含む） | なし | 使える。面接前に「何を見るか」が分かる |
| E2 | 1軸だけ保存する（点＋根拠） | `evaluation_scores` に1行 | 使える。面接中に1つずつ記録できる |
| E3 | 確定する（`submitted` にする） | `evaluations` の2列 | 使える。全軸そろってから通る |
| E4 | 点の訂正 | 未定 | E2 の運用を見てから決める |

**最も小さいのは E1 である。** 書き込みが無く、既存の画面
（`/applications/[id]`）に足すだけで、新しい経路も新しい表も要らない。

いま応募の画面は、判断が下りていない評価に対して
**「判断がまだ下りていないため、点も根拠も無い」**としか出さない。
つまり運転席が「評価する」と言っている相手について、**何を評価するのかが
どこにも出ていない。** ここが最初の穴である。

E1 を次のサイクルで実装する。

## 6. コックピットの継続改善（指示による常時項目）

「オペレーターが今何をすべきか」を最優先に改善し続ける、という指示を受けた。

## 7. 変えないと決めたもの

- **母集団を画面と同じ述語に揃える**（C-20）。A-18 はこの方針に従って
  数え直したからこそ見つかった
- **判定を `src/commands/` に置く**（テストから呼べる場所）。3回使って問題なし
- **氏名や id を URL に入れない。** 結果はコードで返す
- **記録の構造 > 集計の定義 > 画面。** 5サイクルで一度も破っていない
- **森・林・木・幹の旧語**（D-11）。付け替えは MVP が固まってから
