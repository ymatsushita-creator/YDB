## 1. 着手前に確かめたこと

`HANDOFF.md` にこう書いてある。

> クライアント側のライブラリを採用するのは「クライアント境界を新設する」判断と
> 同義になるので、**その判断は単独で示し、他の判断に埋め込まない**

書き込みがこれに当たるなら、機能の実装に混ぜて決めてはいけない。先に確認した。

**当たらなかった。** サーバアクションを素の `<form action={...}>` に渡す形は
サーバコンポーネントの中に置ける。`'use client'` は0件のままで、
**JavaScript を無効にしても動く。** `'use server'` は「サーバで動く関数」の
宣言であって、`'use client'` の対ではない。

状態を持つ対話部品（`useActionState` など）を使う段になったら、
そこで初めて境界の判断が要る。**今回はそこに踏み込んでいない。**

### 確認の途中で見つけた、記録の誤り（F-1）

同じ `HANDOFF.md` にこうも書いてあった。

> クライアント JavaScript を一切配信していない。

**これは誤りだった。** 配信 HTML を見ると `<script src>` が並んでいる
（`react-dom`、`react-server-dom-turbopack`、開発サーバでは devtools）。
App Router は RSC のペイロードを流し込むために React の実行時を必ず配る。

```bash
curl -s http://localhost:3111/cockpit | grep -o '<script src="[^"]*"'
```

**この誤りは、判断を過剰に保守的にしていた。** 「JS を1バイトも配っていない」
という前提で考えると、フォームの送信すら境界の新設に見える。
正しい言い方は**クライアント部品を1つも書いていない**である。
`HANDOFF.md` の当該行はこの版で直した。

なお上は `next dev` の出力で、**本番ビルドで何が配られるかは測っていない。**
測っていないことは書かない。

## 2. 作ったもの

置き場所を3つに分けた。**判定を、テストできる場所に置くため**である。

| 層 | 置き場所 | 役目 |
|---|---|---|
| 判定と更新 | `src/commands/assign.ts` | 事実を確かめて1列だけ更新する。**テストから直接呼べる** |
| 受け渡し | `app/cockpit/actions.ts` | フォームの値を渡し、結果コードを付けて戻す |
| 表示 | `app/cockpit/page.tsx` | `<form>` と結果の通知 |

サーバアクションは Next の実行時が要るためテストから呼べない。
**判定をそこに書くと、いちばん壊れると困る部分がテストの外に出る。**

`src/queries/` に混ぜなかったのは、守るべき規律が違うからである。
読み取りは母集団を間違えても数字がずれるだけだが、書き込みは記録を壊す。
新しい `src/commands/` を作った理由はそれだけで、それ以上の抽象は入れていない。

### 弾くもの

**操作できる母集団を、画面と同じ述語に揃えた。** 更新対象は `v_open_tasks` の
`'assign'` に出ている評価だけで、`evaluations` 直結にしない。
直結すると、画面に出ていない評価を `evaluation_id` の直打ちで触れてしまう。
**フォームの hidden は誰でも書き換えられる。**

| 弾くもの | 返す理由 |
|---|---|
| 取り下げられた応募（数えるが、動いていない） | `not_active` |
| 合格・不合格の済んだ応募 | `not_active` |
| 個人情報削除を受けた人の評価 | `not_active` |
| 提出済みの評価 | `not_active` |
| すでに担当が決まっている | `already_assigned` |
| 非活性化された職員 | `staff_not_available` |
| UUID でない id | `evaluation_not_found` / `staff_not_available` |

**UPDATE は条件付きにした**（`WHERE state = 'pending' AND
interviewer_staff_id IS NULL`）。確認と更新の間に誰かが割り当てても、
0 行更新で終わって**後から来たほうが黙って上書きしない。**

### 結果の返し方

`?assign=ok` のように**コードだけ**を URL に付けて同じ画面へ戻す（PRG）。

**氏名も応募の id も URL に入れない。** URL は履歴にもログにも残るので、
個人が分かる値を置く場所ではない。誰を誰に割り当てたかは、
戻った画面のやることの一覧を見れば分かる。

知らないコードが来たら「何も起きていない」として捨てる。

### 面接官の並び順

**抱えている判断待ちが少ない順**に並べた。偏りが見えないまま選ばせると、
いつも同じ人に積む。`/operations` の「面接官別の負荷」と同じ狙いだが、
こちらは**選ぶその場で**見せる（`宮田 千尋（待ち 0）` のように出る）。

## 5. Product Review（`process.md` の3問）

**1. 運用者がいまできて、前はできなかったことは何か。**

**担当を決められる。** これが初めての「画面から記録を変える」操作である。
やること10件が、画面を離れずに片付く。

**2. 残っている一番の摩擦は何か。**

**残りの3種（評価する / 保留を解く / 担当を替える）がまだ画面の外にある。**
27件のうち10件は片付くが、17件は「何をすべきか分かる」までで止まる。

**3. 一番小さくて一番効く次の変更は何か。**

**「保留を解く」を画面から実行できるようにすること。** 5件あり、
`assign` と同じ型（`src/commands/` に判定、`actions.ts` で受け渡し）が
そのまま使える。更新は `evaluations.state` と `hold_reason` である。

ただし `assign` より1つ重い問題がある ―― **保留を解くと、必須で入っていた
理由が消える。** 0008 で「辞退理由を必須にした」のと同じ規律が
`hold_reason` にもかかっている（`evaluations_hold_reason_required`）。
消す操作を入れるなら、**追記専用の表を足すかを先に決める**必要がある。

「評価する」は範囲が違う。スコアと根拠の入力になるので、
軸ごとの入力欄が要り、`evaluation_scores` への複数行の書き込みになる。
1サイクルには大きい。**分割するなら「保留を解く」が先である。**
