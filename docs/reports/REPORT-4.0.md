## 2. 取り下げられた応募が「選考中」と表示されていた（A-14）★

9か月前に取り下げられた応募が **「選考中」** と出ていた。

原因は、応募の結末がどこにも定義されていなかったこと。画面2枚が、
それぞれ次のラダーを自前で書いていた。

```
合格 → 辞退 → 不合格 → （どれでもなければ）選考中
```

「どれでもなければ選考中」は、遷移が1行も無い応募をすべて選考中にする。
選考開始前に取り下げられた応募（`voided_at` あり、遷移なし）がそこに落ちる。

### 2.1 根は表示ではなく、軸が1本足りないこと

`CLAUDE.md` 2節は「画面で困ったとき、まず疑うのは画面ではなくその手前の
定義である」と言っている。実際そうだった。

| 軸 | 述語 | 意味 |
|---|---|---|
| 数えるか | `v_countable_applications` | 応募が起きた事実として木に数えるか |
| 動いているか | **（無かった）** | いま誰かが判断すべき状態にあるか |

選考開始前の取り下げは **「数えるが、動いていない」**。この組み合わせを
表す述語が無かったため、`v_countable_applications` が両方の役を兼ねていた。

判断待ちと保留がそれを母集団にしていたので、**取り下げた相手の判断を
面接官に催促し続ける**形になっていた。③（いま何が起きているか）と
④（次に何をすべきか）を同時に誤らせる。

同じ根で、隣接する3つも壊れていた。

- `getUnassignedSummary` は `applications` にも `persons` にも結合して
  いなかった。すぐ隣に並ぶ判断待ちとは母集団が違う。**同じ画面の2つの
  数字が、別の母集団から出ていた。** 個人情報削除を受けた人の評価も数える
- `getConflicts` は生の `applications` に結合しており、無効化済みも、
  個人情報削除を受けた応募者の**氏名**も出しうる形だった
- `getHeldEvaluations` は判断待ちと同じ

### 2.2 直し方

`db/migrations/0011_application_outcome.sql`。

- `v_application_outcome` … 応募の結末。判定順は
  **辞退 → 合格 → 不合格 → 無効化 → 選考中**
- `v_active_applications` … いま動いている応募。判断待ち・保留・
  担当未割当・利益相反の母集団をここに揃えた

`v_application_state` の上には作れなかった。あれは
`v_countable_applications` を母集団にしているため、名寄せ誤りで無効化
された応募には行が無く、「合格したあとに無効化された応募」の結末を
引けなくなる。**起きた事実は、数えるかどうかとは無関係に残す**（C-12）。

判定順で2つ決めた。

- **辞退が合格より先。** 合格後に辞退した応募の結末は辞退で、席は空く。
  ファネルの `net_accepted_cum` と同じ扱い。到達した事実のほうは
  `v_application_state.is_accepted` に残っており、消していない
- **無効化は最後。** 合格・不合格・辞退という起きた事実を上書きしない。
  無効化は「その後どう扱うか」の話であって、結末そのものではない

画面側のラダーは両方消した。表示名に写すだけになっている。
「集計対象外」は結末とは別の軸なので、別のバッジとして残した。

**集計は動いていない。** 木と幹の件数は修正の前後で変わらない。
結末の定義は、数える／数えないに触れていない。

## 4. 直したら、別の経路が消えた（A-15）

登場人物の画面を開いたら、`persons.note` に「2026-05-18 に識別された」と
書いたつもりの人が **2026/05/17** と表示されていた。

`src/seed/demo.ts` の `at()`。

```ts
const d = new Date(`${base}T00:00:00+09:00`)  // その瞬間の UTC 日付は前日
d.setUTCHours(hour - 9, minute, 0, 0)          // 前日のまま時刻だけ入る
```

JST 深夜を基準に取ると、その瞬間の UTC 日付は前日になる。そこへ
`setUTCHours` で時刻を入れるので、**どの時刻を渡しても指定日の1日前**に
なっていた。A-1（`::date` が接続のタイムゾーンに依存する）と同じ間違いを、
集計ではなくデータの生成側でやっていた。

**表に出なかった理由のほうが重要である。** 応募は
`at(applicationOpen, day, ...)` から作るので、最初の応募は応募開始日の
前日に発生していた。ところがファネルは応募開始日より前の出来事を初日に
寄せる（0004 の `clamped`）。**丸め込みが辻褄を合わせてしまい、集計値
としては正しく見えていた。** 実行②の「表示の丸めで注記が画面上の嘘に
なった」と同じ形が、今度は集計側で起きていた。

直したら、副作用が1つ出た。**年度のどの期間にも入らない接点が0件に
なった。** あの形は、このずれが偶然に作っていたものだった。

> バグが偶然に作っていた経路は、バグを直すと一緒に消える。

年度の切れ目に届く連絡は実データでは必ずあるので、登場人物に1件を
明示的に置き直した。テストで固定してある。

| 森・林・生涯サマリ | 除外する |
| **木・幹** | **数え続ける** |

**こちらでは決めない。** 残す理屈（削除の依頼は個人情報に対するもので、

どちらにも筋がある。過去年度の応募数と合格数が動く変更なので、
`DECISIONS.md` D-10 に保留として書き、集計は現状のまま（数え続ける）にした。

デモもこの経路を踏ませていない。判断が決まってから C-15 と同じやり方で
登場人物を置く。
