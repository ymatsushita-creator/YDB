## 1. 何をしたか

引き継ぎ時点で「次にやりうること」の筆頭に挙がっていた
**森（`partner_reaches`）が画面のどこにも出ていない**を解消した。

森は原典が定義している段のひとつで、README も「森 → 林 → 木 → 幹 を
同じ場所で見る」と書いている。集計関数 `f_partner_reach_summary` も
実装されていた。にもかかわらず `src/queries/dashboard.ts` からも `app/` からも
一度も呼ばれておらず、**引数ガード以外のテストが無かった**。
呼ばれていない集計は、正しいかどうかを誰も確かめていないのと同じである。

順序は、画面を作る前に集計を検証する形にした。

1. `f_partner_reach_summary` が何を数えているのかをテストで固定する
2. 足りない道具（年度全体の実人数）をデータベース側に足す
3. その上で画面を作る

## 2. 森の集計は定義どおりだった

テストで固定したのは次の性質。いずれも実装は定義どおりに動いていた。

- 推定リーチは合計、接触機会は行数、期間は最初と最後のリーチ日
- `identified_count` は**実人数**。同じ人が同じ団体に複数の接点を持っても1
- 観測窓は「最初のリーチ 〜 最後のリーチ + N 日」。境界日を含む
- 窓の判定は JST。UTC 接続でも端が1日ずれない
- 削除済み Person は数えない（個人情報削除の依頼が森から漏れない）
- 団体をまたいで混ざらない。団体を経由しない接点は森に立たない

→ `tests/11_partner_reach.test.ts`

## 3. 見つけた問題

### 3-1. `identified_count` は行をまたいで足せない

同じ人が2つの団体から接触されていれば、両方の行で1と数えられる。
同じ団体が複数年度にリーチしていれば観測窓が重なりうる。
団体別の指標としては正しいが、**年度全体の実人数を出すつもりで合計すると
重複したまま増える**。

画面で縦に足してしまうのは自然な操作なので、足せないことを
テストと画面の両方に残した。デモデータの2027年度では、団体別の合計が50人、
年度全体の実人数が48人になる。

年度全体を数えるには「どの人が数えられているか」まで戻る必要がある。
画面側で数え直すこともできたが、それだと観測窓の定義がアプリと
データベースの二箇所に散る。`f_partner_reach_persons` を 0009 で足し、
画面はそれを数えるだけにした。定義が2箇所にある状態は残るので、
団体×年度ごとの人数が一致することをテストで固定してある。

### 3-2. 出そうとしてやめた指標

画面を作った直後、KPI に「推定リーチに対する識別率」を置いていた。
2027年度で 2.0%。もっともらしく見えるが、**分母は推定した接触機会、
分子は実人数**で、単位も数え方も違う。

このプロジェクトは 1.1 で、日次の 林 → 木 転換率を
「母集団の定義が日ごとに違うものを割っても分析にならない」という理由で
削除している。同じ性質の数字を森で作っていた。外した。

`estimated_reach` が推定値でなくなるまで、この歩留まりは出さない。

### 3-3. 丸めた値の縦計が合わない

アトリビューション3方式（初回接触・最終接触・線形）を1つの表に並べ、
「3方式は同じ実人数を違う配り方で見るので、合計は3列とも一致する」と
注記に書いた。ところが線形の重みを SQL 側で小数2桁に丸めていたため、
行ごとの誤差が積もって縦計だけ 885.99 になった（他の2列は 886）。

注記が画面上で嘘になっていた。丸めをやめ、合計行は丸める前の値から作る。
実データで3列とも 886 で一致することを DOM から確認した。

## 4. 画面（(4) 流入元 `/sources`）

- **森の KPI** … 推定リーチ（推定値）／接触機会（何団体か）／団体経由で識別（実人数）
- **団体別のリーチ** … 期間・接触機会・推定リーチ・識別（人）。
  識別の列が縦に足せないことと、年度全体の実人数との差を注記に書いてある
- **チャネル別のアトリビューション3方式** … 合計行付き。
  初回と最終が大きく食い違うチャネルは、単独では応募に届いていない
- **見えないものの明示** … 年度に紐づかない団体リーチの件数と、
  どの年度にも属さない接点の件数。どちらも表から消えるので、
  消えたことが分かる形で残す

推定値と実人数を同じ軸に並べていない。森を(3)のファネルにも並べていない。
