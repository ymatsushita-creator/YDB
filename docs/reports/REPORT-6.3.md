## 0. まず、前の版の誤りを訂正する

`REPORT-6.2.md` 7節で、**指示を仰ぐ項目として1つ挙げて止まった。**

> **担当の割り当てに履歴が要るか。** 要るなら追記専用の表を足す。
> **「保留を解く」に進む前に決まっていると早い**（同じ判断が要る）

`process.md` はこう定めている。

> Avoid stopping development for theoretical discussions.
> If a discussion cannot be resolved within two implementation cycles:
> make a reasonable assumption / document it / continue implementation.

**止まったのが誤りだった。** 加えて、止まった理由そのものも誤っていた。

`REPORT-6.2.md` 5節にこう書いた ―― 「保留を解くと、必須で入っていた理由が
消える」。制約を読み直したら、そうではなかった。

```sql
CONSTRAINT evaluations_hold_reason_required
    CHECK (state <> 'held' OR hold_reason IS NOT NULL)
```

これは**「保留なら理由が要る」**であって**「保留でなければ理由を持てない」**では
ない。`state` だけを戻し、**`hold_reason` は残せる。**

**消える値が無いので、履歴の表は要らなかった。** 判断を仰ぐ必要も無かった。
**止まる前に制約を読み直せば済む形だった。**

## 1. 作ったもの

`/cockpit` の「保留を解く」に、ボタンを付けた。やること27件のうち5件。

C-20 で決めた型をそのまま使った。**新しい判断は1つも要らなかった。**

| 層 | 場所 |
|---|---|
| 判定と更新 | `src/commands/unhold.ts` |
| 受け渡し | `app/cockpit/actions.ts` の `unholdAction` |
| 表示 | `app/cockpit/page.tsx` の `UnholdForm` |

更新するのは `state` の1列だけである。**`hold_reason` は残す。**
消すと「なぜ止まっていたか」が記録から失われる。

### 解いた先を決め打ちにしていない

担当が付いていれば「評価する」、付いていなければ「担当を決める」になる。
どちらも `state` と担当の有無から `v_open_tasks` が導く
（原則7「事実の有無で判定し、理由で分岐しない」）。

**実データで最初に解いた評価が、たまたま担当未割当だった。**
解いた瞬間に「担当を決める」のフォームに変わり、そのまま担当を選べる状態になった。
決め打ちで「解いたら評価待ち」と書いていたら、ここで嘘になっていた。

### 弾くもの

`assign` と同じ7種を弾く（取り下げ・不合格・削除済み・提出済み・
二重解除・不正な id）。母集団は `v_open_tasks` の `'unhold'` に揃えた。
`UPDATE` も `WHERE state = 'held'` を条件に入れ、
確認と更新の間に誰かが解いていたら 0 行で終わる。

### 確認を挟んでいない

**失われるものが無い**ので、取り消しの重さに見合わない。
消える操作を足すときに考える。

## 4. Product Review（`process.md` の3問）

**1. 運用者がいまできて、前はできなかったことは何か。**

**止まっていた選考を、画面から動かし直せる。** 27件のうち15件
（担当を決める10・保留を解く5）が画面の中で片付く。前の版は10件だった。

**2. 残っている一番の摩擦は何か。**

**「評価する」10件と「担当を替える」1件が、まだ画面の外にある。**
やることの半分強は片付くが、評価の入力は別の場所でやることになる。

**3. 一番小さくて一番効く次の変更は何か。**

**「担当を替える」を画面から実行できるようにすること。** 1件しかないが、
**`assign` の部品がほぼそのまま使える**（同じ `<select>` で、更新するのも
同じ1列）。違いは「すでに入っている担当を差し替える」ことだけである。

そして**ここで初めて「上書きで消える値」が出る。** 前の担当が誰だったかは、
上書きすると残らない。**履歴の表を足すかどうかの判断が、ここで避けられなく
なる。** 逆に言えば、`assign` と `unhold` で先送りにしてきた判断を、
一番小さい機能（1件）の上で決められる。

「評価する」はスコアと根拠の複数行書き込みで、1サイクルには大きい。
`evaluation_scores` への複数行 INSERT と、軸ごとの入力欄が要る。
**分割するなら「担当を替える」が先である。**

## 6. 学んだこと（`process.md` の Learn）

**何が誤りだったか。** 「保留を解くと理由が消える」という前提。
制約を読まずに、`hold_reason` が必須であることから「解けば消える」と推した。

**何が変わるか。** 止まる前に、**その判断が本当に必要かを確かめる。**
`REPORT-6.2.md` の私は、判断を仰ぐ項目を1つ立てて次のサイクルを止めた。
実際には制約を1行読み直すだけで消える問いだった。

`process.md` の "Avoid Analysis Paralysis" は「2サイクル解決しなければ
仮定を置け」と読める。**が、そもそも問いが立っていないことがある。**
仮定を置く前に、記録層に答えが書いていないかを見る。

**文書を直したか。** `CLAUDE.md` の規律に1行足した ――
**「止まる前に、その判断が本当に必要かを確かめる」。**
制約とコメントに答えが書いてあることが実際にあった、という根拠つきで。
