## 3. DESIGN.md 準拠の確認

指摘を受けて、実行②で書いた画面が `basic/DESIGN.md` に従えているかを機械的に確かめた。

| 確認 | 結果 |
|---|---|
| `pnpm tokens` を再実行し `app/tokens.css` に差分が出ないか | 差分なし（DESIGN.md と一致） |
| `app/base.css` が使う色トークンが DESIGN.md に実在するか | 18件すべて実在 |
| `app/sources/page.tsx` に色・寸法の直値がないか | なし（既存クラスのみ） |
| 実行②で足した合計行のスタイル | **トークンから外れていた。修正した** |

**見つけた逸脱は1件。** アトリビューション表に足した合計行（`table.data tfoot th`）に
`line-height` を指定しておらず、DESIGN.md の `caption-bold`（13px / 600 / 1.4）から外れていた。
`line-height: 1.4` を足し、ブラウザの計算値で確認した（13px / 600 / 18.2px /
letter-spacing なし / `#1a1a1a` = ink / border `#e5e3df` = hairline）。
同じ画面の `card-base` も radius 12px（rounded.lg）・padding 24px（spacing.xl）で定義と一致していた。

字面の判断（列見出しの `micro-uppercase` ではなく `caption-bold` に寄せる）にも
理由をコメントで残した。列見出しと同じ字面だと、合計が見出しの一部に見えるため。

## 4. `CLAUDE.md` の制定 ★この実行の中心

**この開発が何のためのものかを、毎セッション最初に読まれる場所へ刻んだ。**

### 4-1. 達成すべきこと

担当者が誰であっても、候補者が誰であっても、次の4つが一発で直感的に分かること。

1. 誰がどんな状態か
2. 誰が何を評価したか
3. いま何が起きているか
4. 次に何をすべきか

この4つに答えられない機能は、どれだけ作り込んでも価値がない。
逆に、この4つに効くなら地味な表でよい。

### 4-2. 選考プロセスドリブンであること

**主題は UI の充実やデザインの良し悪しではない。**
記録と集計の構造そのものが、集客から選考までの一連の流れを
「評価し、計画を考え、実行する」に足りうるものになっているかが主題である。

優先順位を次の順に固定した。

```
記録の構造（何を事実として残すか）
  > 集計の定義（その事実をどう数えるか）
    > 画面（数えた結果をどう見せるか）
```

画面で困ったとき、まず疑うのは画面ではなく手前の定義。
実行①〜②で見つかった重い欠陥は、実際すべて記録層と集計定義の側にあった。

### 4-3. 森・木の比喩の位置づけ

比喩とアイコンは、4つの問いに一目で答えさせるための**手段**である。
装飾でもなく、数字の代わりでもない。守る規律を4つ書いた。

- 単位の違うものを同じ軸に置かない。並べても割らない
- 絵は必ず数字と併置する（森ビューは表とカードの代替ではなく補助）
- 可視化コンポーネントに SQL を書かせない
- 個体を描くときの表示用 seed は鍵付きハッシュから作る

### 4-4. 完了の定義

テスト全通過・型チェック・実データでの確認（目視ではなく DOM か SQL の値）・
単位と母集団の注記・`DECISIONS.md` への記録に加えて、最後に一項目を置いた。

> **4つの問いのどれに効いたかを一言で言えること。**

## 5. いまの構造で、4つの問いに答えられているか

`CLAUDE.md` 8節に実測の表を置いた。**主題が構造である以上、この表を最新に保つ。**

| 問い | 記録層 | 集計 | 画面 |
|---|---|---|---|
| ① 誰がどんな状態か | あり | `v_person_season_state` | **年度の集計のみ。個人を引く画面が無い** |
| ② 誰が何を評価したか | あり | 面接官別の負荷まで | **応募1件の評価履歴を見る画面が無い** |
| ③ いま何が起きているか | あり | 滞留・未割当・保留・利益相反 | `/operations` にある |
| ④ 次に何をすべきか | 部分的 | 滞留の一覧まで | **「次の一手」を提示する仕組みが無い** |

構造側に残っている穴は4つ。

1. **個人・応募のドリルダウンが存在しない。** `src/queries/dashboard.ts` の16の問い合わせは
   すべて年度単位の集計で、Person 1人 / Application 1件を引くものが無い。
   ①②に直結する最大の穴だが、**記録層は既に足りている**（集計と画面が無いだけ）
2. **`reject` にステップが結び付いていない。** 列はあるが運用でもデモでも埋めていないため、
   どのステップで落ちたかを集計できない。推測で埋めない
3. **`is_reapplication` の再計算処理が無い**（実装段階[4]）。年輪の表示はそれまで保留
4. **`seasons` の実数値が未確定**（D-8）。計画を立てる土台そのものが空
