# Pilot Deployment Readiness — 現状の実測（実装前）

2026-08-07。**この文書は実装ではなく測定の報告である。**

目的: 社長・運営担当者が**ローカル環境なしで URL から安全に試運転できること。**

成功条件（指示より）—— 運営担当者が自分の端末から URL を開き、**実データで
採用フローを1周でき、障害や誤操作が起きてもデータを復旧できること。**

すべて実際に動かして確かめた。推測は「未確認」と書く。

## 3. ブロッカー（これが解けないと URL 試運転が成立しない）

### B-1. データが保存されない ★最大

`getDb()` は `process.cwd()/.pgdata` を開く。**PGlite はローカルの
ファイルシステムに書く。**

- **サーバレス（Vercel など）では成立しない。** ファイルシステムは揮発し、
  インスタンスごとに別である。**運営が入力した担当・点・判定が消えるか、
  別の人には見えない**
- `DATABASE_URL` を設定すると `src/db/server.ts` が**意図的に throw する**
  （PostgreSQL アダプタ未実装）

**これは設定ではなく、デプロイ先の選択とセットの判断である。** 4節に選択肢。

### B-2. 認証が無い ★

`middleware.ts` は無く、どのページも素通りである。
**URL を知っていれば誰でも**

- 実在の候補者の氏名・評価・根拠を**読める**
- 担当変更・点の保存・判定・訂正を**書ける**

Pilot は実データで行う予定なので、**URL 一つで個人情報が公開される。**
`HANDOFF.md` は「認証を持たないのは設計判断」と書いているが、
それは**ローカル前提の判断**である。公開する時点で前提が変わる。

### B-3. Pilot DB を消す事故を防ぐ装置が無い ★

```ts
await rm(DATA_DIR, { recursive: true, force: true })   // scripts/db-reset.ts
```

**確認も環境判定も無い。** `pnpm db:reset` を打った瞬間に全消しである。
開発と Pilot で同じコマンド・同じパスを使うため、**取り違えは起こりうる。**
実際、この開発中に**開発サーバを起動したまま触って `.pgdata` を2回壊している。**

### B-4. 復旧できない

バックアップが無いので、B-3 が起きたら**戻せない。**
成功条件の後半（障害や誤操作が起きてもデータを復旧できる）を満たさない。

### B-5. 実データがまだ無い（既知・別ブロッカー）

年度・ステップ・評価軸が本番シードに無い（D-8）。
社長の DB を受け取る段取りは `DATA-INTAKE.md` にある。**判定は HOLD のまま。**

## 4. デプロイ先の選択（決めていただきたい1点）

**B-1 の解き方が2通りあり、コストと工数が違う。** どちらも「新機能」ではない。

### Option A — 1台のコンテナ／VM ＋ 永続ディスク（PGlite のまま）

- **コード変更: ほぼ不要。** いまの `.pgdata` をマウントしたボリュームに置くだけ
- Fly.io / Render / Railway / 自前 VPS など、**永続ディスクを持てる形**
- **制約**: インスタンスは**1台に固定**する必要がある（PGlite の dataDir に
  プロセス間ロックが無い。2台になると壊れる）。Pilot の同時利用は数人なので実用上は足りる
- バックアップはディスクのスナップショット＋`.pgdata` の tar で取れる
- **工数: 小**

### Option B — マネージド PostgreSQL（Neon / Supabase など）＋ どこでも動くホスティング

- **`src/db/server.ts` に PostgreSQL アダプタを書く**（`Db` は3メソッドなので小さい）。
  コメントに「本番で PostgreSQL に繋ぐときは…」と最初から書いてある想定の実装
- サーバレスでも動く。バックアップは提供側の機能で取れる（時点復元つき）
- **制約**: 依存が1つ増える（`pg`）。接続数の管理が要る
- **工数: 中**

### 私の見立て

**Pilot には Option A で足りる。** 利用者は数人、期間は限定、
**いちばん重要なのは「消えないこと」と「戻せること」**であって、
スケールではない。Option B は 1.0 の計画で決めればよい。

**ただし、これは費用と運用体制の話なので決めていただきたい。**

## 5. Pilot に必須なものだけ（実装の順序案）

デプロイ先が決まってから、**1つずつ**進める。**新機能は足さない。**

| # | やること | なぜ Pilot に必須か | 工数 |
|---|---|---|---|
| 1 | **`db:reset` の事故防止** | B-3。**先に入れる。**これが無いまま実データを入れると、1コマンドで消える | 小 |
| 2 | **バックアップと復元の手順＋コマンド** | B-4。成功条件の後半そのもの | 小 |
| 3 | **認証（最小）** | B-2。実データを公開する以上、省けない | 小〜中 |
| 4 | **Pilot DB の分離（環境変数でデータ位置を分ける）** | 開発の操作が Pilot に届かないようにする | 小 |
| 5 | **本番のマイグレーション手順（全消しでない導線）** | 2 の復元とセットで要る | 小 |
| 6 | **エラーの確認方法**（`error.tsx` とログの出力先） | 障害時に「何が起きたか」が分からないと戻せない | 小 |
| 7 | **公開環境での E2E 手順** | 実データで1周できることを、URL 上で1回通す | 小 |

**1 と 2 を最初にやる。** 順序の理由は、**取り返しがつかない事故を先に塞ぐ**ため。
認証より先である ―― 認証が無くても消えたデータは戻らないが、
バックアップがあれば認証の穴は「読まれた」で済む（それも避けたいが、可逆性が違う）。

**7 が終わった時点で、URL 試運転の準備が整う。**
そこから `docs/pilot/CHECKLIST.md` の実施に入る。

## 6. 実装しないと決めたもの（Pilot には要らない）

- **ユーザーごとのログイン**。誰が操作したかを画面から取る仕組み。
  Pilot は立ち会いで観測するので、共有の合言葉で足りる
- **HTTPS の自前設定**。ホスティング側の既定に任せる
- **監視・アラート**。Pilot の期間と規模では、立ち会いのほうが早い
- **PostgreSQL への移行**（Option A を選ぶ場合）。1.0 の計画で決める
- **自動デプロイ（CI/CD）**。手で 1 回上げれば足りる
