# Pilot Exit Criteria — Pilot を終える条件

**Pilot は無期限に続けない。** Version 1.0 の計画を**自信を持って始められる
だけの証拠**が揃った時点で終える。

**成功を機能の数で定義しない。** 定義するのは
**「実際の運営担当者が、採用業務を確実に回せると確信できるか」**の1点である。

この文書の出力は **Go / Hold / No-Go** の1つである。判定は依頼する側が下す。
開発者は**チェック欄を埋めるだけ**で、埋まっていない欄を「たぶん大丈夫」で
通してはならない。

> ## 現在の判定: **HOLD**（2026-08-07）
>
> 理由は品質ではなく**運用上の証拠が無いこと**。
> 全文と、この判定で示された4つの Go 条件は `docs/pilot/DECISION-LOG.md`。
>
> **基準を緩めて Go にしない**（同日の指示）。
> 1-1 の人数について本判定と数が違う（2名以上 / 1名以上）。
> **寄せずに `DECISION-LOG.md` に残し、確認を待っている。**
> 確認が取れるまでは**厳しい側（2名）で準備する。**

---

## 0. 用語の定義（数える前に固める）

数える単位が曖昧だと、条件は満たしたことにできてしまう。

| 語 | 定義 |
|---|---|
| **運営担当者（operator）** | 実際に採用業務を担当する人。**社長と開発者は含まない。**「初めて触る人」も含まない |
| **1周（recruiting cycle）** | 1つの応募について、運転席のやること1件から始めて **評価 → 確定 → 判定** まで到達したもの。**操作を教えられずに**通したものだけを数える |
| **観測1件** | `OBSERVATION-SHEET.md` の 1〜4・8 に書かれた**1行**。時刻と場所が入っているもの。あとから記憶で足したものは数えない |
| **Validated Operator Problem** | `REVIEW.md` 3 の昇格条件4つをすべて満たしたもの。**要望・感想・開発者の気づきは含まない** |
| **飽和（saturation）** | 最後のセッションで、**新しい種類**の観測が2件以下だったこと |

---

## 1. 定量条件

### 1-1. 運営担当者の人数

- [ ] **運営担当者 2名以上**が、それぞれ1周以上を通した
- [ ] うち**1名以上**が、**別の日に2回目**のセッションを行った
- [ ] **初めて触る人 1名以上**が、語の理解を試された（`CHECKLIST.md` 3）
- [ ] **社長 1名**が未決の判断に答えた

**なぜ2名か。** 1名では「その人の癖」と「画面の誤り」を区別できない。
2名が同じ場所で迷えば画面の問題、1名だけなら癖の可能性が残る。

**なぜ別の日か。** 滞留日数・SLA・期限超過は**日をまたがないと現れない。**
これまでの検証はすべて同日で、`jst_today()` に依存する表示が
実運用でどう見えるかを**一度も観測していない。**

### 1-2. 採用サイクルの回数

- [ ] **1周を合計5回以上**（運営担当者による。教えられずに通したもの）
- [ ] うち**1回以上**が**合格**（最終ステップの通過）まで到達した
- [ ] うち**1回以上**が**不合格**で終わった
- [ ] うち**1回以上**が**面接官2名のステップ**を含んだ
- [ ] うち**1回以上**で**判定の訂正**が行われた
- [ ] うち**1回以上**が**複数日にまたがった**（初日に評価、別日に判定）

**合格と不合格の両方が要る理由。** 到達する記録が違う（合格は
`v_application_state.is_accepted`、不合格は `reject` とステップ）。
片方だけでは半分しか確かめていない。

### 1-3. 観測の件数

- [ ] 観測の合計が **20件以上**
- [ ] うち「手が止まった」＋「迷った」が **8件以上**
- [ ] 「実際に使った言葉」が **15語以上**（翻訳せずに記録されたもの）
- [ ] 「自然に理解できた場所」が **5件以上**
      （**壊さないために要る。** 改善点しか集めていない記録は使えない）
- [ ] 「画面の外に書きたくなったもの」が **3件以上**、または
      **明確に0件だと確認できた**（訊いて出なかった）
- [ ] **飽和に達した** ―― 最後のセッションで新しい種類の観測が2件以下

**「手が止まった＋迷った」が8件未満なら、Pilot はまだ終えられない。**
プロダクトが完璧なのではなく、観測が取れていないと考える
（`OBSERVATION-SHEET.md` 11）。

### 1-4. 残っている Validated Operator Problem の数

**0件を求めない。** 求めるのは**分類と決定が済んでいること**である。

| 影響の種類 | 残していい数 | 条件 |
|---|---|---|
| **業務が止まる** | **0件** | 1件でも残っていたら Go にしない |
| **数字が間違う** | **0件** | 同上（画面の数字が嘘をつく状態で 1.0 の計画は立てられない） |
| 迷うだけ | **3件以下** | 各件に**決定**が付いていること |
| 見た目・語感 | 制限なし | 一覧化されていること |

- [ ] 「業務が止まる」の Validated が **0件**
- [ ] 「数字が間違う」の Validated が **0件**
- [ ] 「迷うだけ」の Validated が **3件以下**
- [ ] 残っている Validated **すべて**に決定が付いている
      （**いま直す** / **1.0 で直す** / **直さないと決めた**のいずれか）

**「直さないと決めた」も合格である。** 決まっていないものが残っているのが
不合格の状態である。

## 2. 定性条件

数で測れないが、これが欠けていたら Go にしない。

- [ ] **運営担当者が、次の朝もこの画面を開くと言った**（言葉で確認する）
- [ ] **運営が画面の外で回していた業務が、何であるかを言える**
      （無いなら「無い」と確認済み）
- [ ] **語の食い違いが `domain.md` 10節に渡っている**（`REVIEW.md` 5）。
      未決のまま残すのは構わないが、**渡っていない語がゼロ**であること
- [ ] **「操作を教えた回数」が最後のセッションで 0 回**
      （教えないと通らない状態は、まだ画面が答えを出していない）
- [ ] **開発者が、運営の1日を自分の言葉で説明できる**
      ―― 何から始め、何で終わり、どこで待たされるか
- [ ] **崩れた前提が1つ以上ある**（`Invalidated Assumptions` が空でない）。
      1つも崩れなかった Pilot は、観測が薄い可能性が高い

---

## 3. 実データの条件（Go の必須条件）

- [ ] **実データで1周以上を通した**

**いまこれは満たせない。** 本番シードには `withdraw_reasons` しか入っておらず、
**年度・選考ステップ・評価軸が1行も無い**（`DECISIONS.md` D-8）。
本番データベースを開いても画面は空になる。

**ブロッカーはコードではなく情報である** ―― 年度の実数値（入学年・集客開始・
応募開始・応募締切・選考終了・定員・目標応募数）。
`CHECKLIST.md` 1 の質問3で取る。

**実データでの1周が無いまま Go にはしない。** 理由は、いま最も分かって
いないことが「**画面の数字が実感と合うか**」であり、デモデータは架空なので
**この Pilot の設計上、そこは学習できない**からである。
数字の妥当性を確かめずに 1.0 の計画を立てると、母集団と単位の議論を
計画のあとにやり直すことになる。

## 4. Pilot を直ちに終える条件

該当したら、**残りのセッションを行わずに**判定へ進む。

### 4-1. 直ちに **No-Go**（根本的なワークフローの問題）

- [ ] **記録が壊れた。** 運営の操作で、集計が説明できない値になった
      （例: 同じ年度で林 < 木、合格者数が定員を超える、履歴の順序が矛盾する）
- [ ] **運営が画面を選ばなかった。** 1周できるにもかかわらず、
      **実際の業務では画面外の手段を使い続けた**
- [ ] **同じ場所で 3人中3人が止まった。** ワークフローの前提が運用と違う
- [ ] **個人情報が意図せず見えた。** 削除依頼を受けた人の氏名が画面か URL に出た
- [ ] **1周が誰も通せなかった**（操作を教えても通らない）

**No-Go は「作り直し」を意味しない。** 「いま 1.0 の計画に進めない」という
判定である。何が根本かを特定し、**Pilot の前の段（記録の構造か集計の定義）**へ戻る。

### 4-2. 直ちに **Hold**（証拠が足りないと確定した）

- [ ] 実データが**用意できないと確定した**（3節が満たせない）
- [ ] 運営担当者が**1名しか確保できないと確定した**

この場合、**足りない証拠に名前を付けて**待つ。曖昧に続けない。

---

## 5. Pilot を延長する条件

該当したら、セッションを追加する。**判定を先に出さない。**

- [ ] **飽和していない**（最後のセッションで新しい種類の観測が3件以上）
- [ ] 観測が **20件未満**
- [ ] 「手が止まった＋迷った」が **8件未満**
- [ ] 全セッションが**同日**に行われた（1-1 の別日条件が未達）
- [ ] **合格または不合格のどちらかに到達していない**
- [ ] **立ち会いで操作を教えた回数が多い**
      （`OBSERVATION-SHEET.md` 10。観測が薄い）
- [ ] **Validated が0件**（`REVIEW.md` 6-4。運びを直してやり直す）
- [ ] Validated に**決定が付いていないもの**が残っている

---

## 6. Go / Hold / No-Go の判定

**順に見る。上で該当したら、下は見ない。**

### 手順

```
1. 4-1 の No-Go 条件に1つでも該当するか   → はい: No-Go
2. 4-2 の Hold 条件に1つでも該当するか    → はい: Hold（足りない証拠を明記）
3. 5 の延長条件に1つでも該当するか        → はい: Hold（追加セッションを設定）
4. 1・2・3 のチェック欄がすべて埋まったか → はい: Go ／ いいえ: Hold
```

### 判定の意味

| 判定 | 意味 | 次にすること |
|---|---|---|
| **Go** | Pilot の目的を達成した。**運営が採用業務を確実に回せると確信できる** | Version 1.0 の計画に入る。残った Validated（迷うだけ・見た目）を計画へ持ち込む |
| **Hold** | **運営の証拠がまだ足りない。** プロダクトの否定ではない | 足りない証拠に名前を付け、追加セッションを設定する。**この間に新機能を作らない** |
| **No-Go** | **根本的なワークフローの問題**が見つかった | 記録の構造か集計の定義へ戻る。画面の修正で済ませない |

**Hold と No-Go の違い。** Hold は「まだ分からない」、No-Go は「分かった、
そして違っていた」である。**Hold を No-Go の代わりに使わない** ――
根本の問題を「証拠不足」と呼び替えるのが、いちばん高くつく間違いである。

## 8. この文書の使い方についての注意

- **チェック欄を「たぶん満たしている」で通さない。** 埋まっていない欄は
  未達である。数えられないものは数えられないと書く
- **機能の数を判定に使わない。** 「あと3つ作れば Go」という考え方をしない。
  残っている機能があっても、業務が確実に回るなら Go である
- **Go のあとも Validated は残っていてよい。** 1.0 の計画に持ち込む
- **判定は依頼する側が下す。** 開発者はシートを埋め、
  **埋まらなかった欄を隠さない**
