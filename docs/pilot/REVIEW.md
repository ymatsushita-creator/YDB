# Pilot 終了後のレビュー手順

**目的は次に作るものを決めることではない。** 何が**分かったか**を確定させ、
そのうえで初めて次を選ぶ。

**Developer Hypothesis を自動的に Validated へ昇格させない。**
これがこの手順のいちばん重要な規則である。

---

## 手順

### 1. シートを合わせる（開発者・全員分）

対象者ごとの `OBSERVATION-SHEET.md` を並べ、**1〜4 と 8 の行に通し番号を振る。**
これが以降で参照する「観測」の単位になる。

観測1件 = 1行 = 「いつ・どこで・誰が・何をしたか」が書かれているもの。
**書かれていないものは観測として数えない。**（記憶で足さない。
「たしかあのとき迷っていた」は、次の Pilot で取り直す）

### 2. 分類する

すべての課題を4つに振り分ける。**既存の課題（`REPORT-6.10` の一覧）も
毎回この手順を通す** ―― 前回 Developer Hypothesis だったものが、
今回の観測で Validated になることがある。

| 分類 | 定義 |
|---|---|
| **Validated Operator Problem** | **観測された運営の行動**によって存在が確かめられた問題 |
| **Developer Hypothesis** | 開発者が気づいた／推論した問題。**観測の裏づけが無い** |
| **Technical Debt** | 運営には見えない内部の負債 |
| **Product Backlog** | まだ必要と確認できていない機能 |

### 3. 昇格の条件（ここを厳しく守る）

**Developer Hypothesis → Validated Operator Problem** は、
次の**すべて**を満たしたときだけ動かす。

- [ ] **運営の行動**が観測シートの 1〜4 または 8 に記録されている
      （止まった／迷った／押し間違えた／想定外の操作／画面の外に書いた）
- [ ] その行に**時刻と場所**が入っている
- [ ] その行動が、**画面の作りに起因する**と説明できる
      （デモデータが架空であることに起因する迷いは**除く**）
- [ ] 記録が**当日中**に書かれている（あとから思い出して足したものは含めない）

### 昇格させてはいけないもの（よく間違える）

| 材料 | 扱い | なぜ |
|---|---|---|
| 「○○があったら良いですね」 | **Developer Hypothesis のまま** | **要望は観測ではない。** 言葉は安く、行動は高い |
| 「これは分かりにくいですね」（操作は詰まらなかった） | Hypothesis のまま | 感想であって行動ではない。ただし**迷いが記録されていれば**昇格する |
| 開発者が1周通して気づいたこと | Hypothesis のまま | 開発者は運営ではない |
| 数字が実感と合わない | **除外** | デモデータが架空だから当たり前。実データでの Pilot まで判定できない |
| 団体名・氏名が知らない名前だ | **除外** | 同上 |
| こちらが操作を教えた場所 | **昇格する** | 教えたという事実が、画面が答えを出せなかった証拠である |

**判断に迷ったら昇格させない。** 昇格しなかったものは消えない ――
Hypothesis として残り、次の Pilot でまた試される。
**急いで Validated にすることの利益は無い。**

### 4. Validated のものに、頻度と影響を付ける

昇格したものだけ、次を記録する。**推測で埋めない。**

| 項目 | 書き方 |
|---|---|
| 観測回数 | 何人中何人で起きたか（例: 3人中2人） |
| 1人あたりの回数 | 1周のうち何回起きたか |
| 影響 | 業務が止まる / 数字が間違う / 迷うだけ / 見た目 |
| 頻度の根拠 | **観測**（何人中何人）か、**推論**か。推論なら「頻度は未観測」と書く |

**頻度が未観測でも Validated ではありうる。** 存在（1回でも起きた）と
頻度（どれくらい起きるか）は別の事実である。混ぜない。

### 5. 言葉の食い違いを処理する

シートの 7 に「違う」が付いた語は、**画面の言い換えで済ませない。**

1. 相手の語を**そのまま** `domain.md` 10節へ未決として足す
2. こちらの語との関係（同じ／違う／一部重なる）を書く
3. **どちらが正しいかを決めない。** 決めるのは依頼する側である

`CLAUDE.md` の規律「同じ言葉を2つの定義で使わない」に触れるので、
実装の言い換えは**世界設定が決まってから**行う。

### 6. 次のスプリントを選ぶ

**優先順位の最大値ではなく、学習量あたりの実装量で選ぶ**（Pilot Phase の規則）。

順に見る。

1. **業務が止まる Validated Operator Problem があるか** → あればそれ
2. **数字が間違う Validated Operator Problem があるか** → あればそれ
3. どちらも無ければ、**次の Pilot で学習量が最大になるもの**を選ぶ
   （観測が取れていない場所を触れるようにする、など）
4. Validated が0件だったら、**実装せずに Pilot の運び方を直す**
   （シートの 10 を見る。教えすぎ・誘導・時間不足のどれか）

**「Hypothesis が多いから、そのうち1つを作る」は選び方として禁止。**
それは観測の代わりに勘で決めることである。

### 7. 報告書を書く

`docs/pilot/REPORT-TEMPLATE.md` を使う。版は `REPORT-<実行番号>.<連番>.md`。
書いたら凍結する。記録（`db/DECISIONS.md`）と `HANDOFF.md` は更新する。

---

## レビューの成否

| 条件 | 判定 |
|---|---|
| すべての課題が4分類のどれかに入った | |
| 昇格したものすべてに、観測シートの行番号が付いている | |
| 昇格させなかった Hypothesis に、**なぜ昇格しないか**が1行ずつ書いてある | |
| 言葉の食い違いが `domain.md` へ渡った | |
| 次のスプリントの選び方が、上の 6 のどの番号によるか書いてある | |

**Validated が0件でも、レビューは成功しうる。**
「観測が取れなかった」と分かることも学習である。
**取れなかったのに Hypothesis を昇格させたら、そのレビューは失敗である。**
