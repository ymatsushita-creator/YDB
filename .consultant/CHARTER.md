# コンサル基準書（CONSULTANT CHARTER）

本書はコンサル（分析・実働側）の文書である。**監査（`.audit/`）とは分離している。**

道具の実体: `../コンサル/bin/consultant`（`analyze` / `configure` / `prompt` / `run`）
位置は `.consultant/TOOL_PATH` に固定する（`.audit/TOOL_PATH` と同じ形）。
本書の基準を機械にしたものが `scripts/check-structure.ts`（`pnpm structure`）である。

## 1. 権限の位置

```text
.audit/       監査 —— 何を出してはならないか        【最高権限】
    ↓ すべてに優先する
.consultant/  コンサル —— どう作れば速く安全に回るか  【本書の層】
    ↓ 既存の方針文書に優先する
SUPERVISOR.md > vision.md > director.md > domain.md > CLAUDE.md > process.md
```

- **本書は `.audit/` に劣後する。** 食い違ったら監査が勝つ。
  「開発速度のために」を理由に監査要求を退けてはならない。
  監査が Critical / High を出している間、本書の改善提案は着手の理由にならない。
- **本書は既存の方針文書に優先する。** 構成・工程・完了条件について本書と
  `CLAUDE.md` / `process.md` が食い違う場合、本書に寄せて下位文書を直す。
- ただし**プロダクトの中身**（`vision.md` の目的、`director.md` の原則、
  `domain.md` の用語）に本書は口を出さない。本書が扱うのは**作り方の構造**だけである。

## 2. 監査との役割分担

| | 監査（黒崎） | コンサル（本書） |
|---|---|---|
| 問い | 出してはならない物が出ていないか | 速く安全に回る構造になっているか |
| 初期仮説 | 「この変更には問題がある」 | 「この構造には無駄と穴がある」 |
| 出力 | 意見（適正／限定付適正／不適正／意見不表明） | 診断スコアと是正項目 |
| 強制力 | フック・CI・deploy-gate が機械で止める | `pnpm structure` と CI の品質ゲートが止める |
| 改竄検知 | `.audit/MANIFEST.sha256` で封印 | **封印されない**（下記 5） |

**基準を重複させない。** 個人情報・秘密・不可逆操作・公開範囲の**基準を定めるのは監査**であり、
本書はそれを再定義しない。

ただし本書は、**監査が定めた基準が構造として保たれているかを見る**（`STRUCTURE.md` §4・§6）。
「実データを外に置く」と決めるのは監査、「外に置かれ続けているかを毎回機械で確かめる」のがコンサルである。
この区別を崩して独自の基準を作らないこと。食い違えば監査が勝つ。

## 3. 検査領域（`consultant analyze` の C01〜C07）

| ID | 見るもの |
|---|---|
| C01 | プロジェクト指示（`CLAUDE.md`）にコマンド・境界・完了条件があるか |
| C02 | 入口文書（`README.md`）に目的と起動手順があるか |
| C03 | 主要経路の自動テストが在るか |
| C04 | CI が在るか |
| C05 | Claude Code の権限設定（許可／拒否）がプロジェクト設定で固定されているか |
| C06 | 調査とレビューの役割がサブエージェントとして分離されているか |
| C07 | 秘密を除いた環境変数の契約（`.env.example`）が在るか |

**C01〜C07 は在ることしか見ない。** 中身が機能しているかは見ない。
実際、2026-08-19 の診断では C04 が通過していたが、CI の中身は監査だけで、
`pnpm test` はどこでも走っていなかった。
**スコア100は「穴が無い」ではなく「既知の穴が無い」である。**
在ることの確認で満足しない —— それが本書 `STRUCTURE.md` の役割である。

## 4. 原則

1. **リポジトリ固有の短い指示を1枚持つ。** コマンド・境界・完了条件を `CLAUDE.md` に置く。
   長い経緯は別の場所（`docs/reports/`）へ出し、着手時に読む物と混ぜない。
2. **計画 → 狭い実装 → 型検査/テスト/ビルド → 独立レビュー**を標準工程にする。
   実装した本人の申告を完了の根拠にしない。
3. **危険操作は設定で拒否する。** 精神論ではなく `.claude/settings.json` で落とす。
4. **反復作業は資産にする。** 2回以上やる手順はコマンド（`.claude/commands/`）へ。
5. **自動化は非対話・ターン上限・構造化出力で回す**（`consultant run`）。
   呼出元が結果を機械で処理できる形にする。
6. **参照される番号には索引を用意する。** 番号で指す設計なら、番号から引ける表が要る。

## 5. 本書の限界（正直に書く）

- **本書は `.audit/MANIFEST.sha256` に登録されていない。**
  したがって書き換えても D7-01 では検知されない。監査層と違い、
  **本書の不可侵性は機械で担保されていない。**
- 本書を実装セッションのAIが書き換えられる、という事実は残る。
  対処は運用側にある —— 変更は人間のコミットとして記録し、差分を読むこと。
- `consultant analyze` は7項目の存在確認であり、監査ではない。
  **「診断100点」を安全の根拠として使ってはならない。**
