## AI駆動開発の観点での所見

### 1. 着手コストは妥当。**「なぜ」の層が読めない**のが本題である

着手時に読む9本は 34,197字 ≒ **22,800トークン相当**で、毎セッション読んでも支障はない。

問題はその先にある。

```
db/DECISIONS.md   496,136字 ≒ 33万トークン相当
```

**どの文脈長にも入らない。AIはこの層を読めない。**
読めないものは参照されず、参照されないものは更新されない。
実行⑯・⑰の44件が記録されずに終わったのは、この構造と地続きである。

対処として `pnpm decisions:show <番号>` を置いた（49万字 → 5,494字。**90分の1**）。
索引が番号から行へ、本書が行から本文へ辿るので、**全文を開かずに到達できる。**

根治はファイルの分割だが、`CLAUDE.md`（封印下）が `db/DECISIONS.md` を
「設計判断の本体」として4箇所で名指ししている。**分割には憲法の書き換えと再封印が要る**
（人間の判断。→ 残っている穴 6）。

### 2. 番号を「使う」ことは強制できるが、「書く」ことは強制できない

CI は索引のずれを `--check` で落とす。だが**最初から書かれなかった判断**は検知しようがない。
コードにコメントを書いた時点では、まだ何もコミットされていない。
現状の唯一の防壁は、索引の先頭に欠番が毎回掲げられることである。

これは検査の穴ではなく、**工程の穴**である。機械で塞ぐなら
「`C-` 番号を新規に導入する差分は、同じ差分で `DECISIONS.md` に見出しを足す」
という pre-commit 段の判定になる（未実装。`.githooks/` は監査法人の管轄）。

### 3. 記録の連鎖が実行⑮で切れている

`docs/reports/` は REPORT-15.1（実行⑮）で止まり、コードは実行⑯・⑰ を指す。
**2回の実行が、報告書も設計判断も残さずに終わった。**
`db/DECISIONS.md` の穴と `docs/reports/` の穴は、同じ穴の両側である。

`pnpm decisions:missing` が、参照元のコードから手がかりを集めて実行ごとに束ねる
（実行⑯ 2件 / 実行⑰ 23件 / 手がかりなし 20件）。**中身は作らない。**

### 4. 設計判断が単一ファイルへ集中していた（解消）

`app/base.css` は 2,366行で、`C-` 番号の参照が 28箇所あった。
CSSを1行直すたびに全体を読むことになり、意匠の判断が1本に閉じ込められていた。
取り込み順（＝カスケード順）を保ったまま `app/_styles/` の10本へ分割した。

**出荷されるCSSは分割前と1バイトも違わない**ことを、ビルド出力の比較で確認した。
その過程で、1本のときは最適化に隠れて見えなかった**デッドコード1件**が表に出た
（`.hh-col-side` の `grid-template-rows` が後段の C-190 に無条件で上書きされていた。
出荷物には元々入っていない）。削除した。

テスト7本が `app/base.css` を直読みしていたので `tests/support/css.ts` へ寄せた。
見るべきは**ブラウザが受け取る1本**であって入口のファイルではない。
以後どう割り直してもテストは追随する。

### 5. 診断層そのものが肥大していた

本書は第4次〜第8次の追記で 148行 → 401行へ膨らんだ。
`.consultant/` は `CLAUDE.md` に「構成・工程・完了条件について本書に優先する」と

### 6. `.md` の配置 —— 凍結が8割を占め、正典が語彙を説明していなかった

```
.md 75本 / 21,935行
  凍結（docs/reports・pilot）  499,679字  ← 全体の80%
  着手時に読む9本               34,197字
  規律・基準・命令              91,149字
```

**凍結が支配的である。** 「着手時に読む物ではない」は `docs/reports/README.md` に
しか書かれておらず、目次を開いた人にしか伝わらない。AIは grep で探すので、
現行文書より先に凍結文書へ当たる。実際 `design.md`（実行⑨で削除）を現役のように
書いた文書が5本あった。35本すべての先頭に但し書きを入れ、**S12 で機械にした**。
但し書きには「では何が正か」と `pnpm decisions:show` の引き方まで書く ——
grepで1ファイルだけ拾った相手に届かせるため。

**`domain.md` は「現行ドメイン語彙の唯一の正典」を名乗りながら、
コードが使う語を説明していなかった。** 旧生態系比喩は
`森` 179 / `林` 152 / `木` 56 箇所に残っているのに、正典側に対応表が無い。
`C-45` を引いても「…に統一した」とあるだけで写像が無い。
記録（D-3・`db/migrations/0002_views.sql`・`src/queries/`）から対応を確定させた。

`domain.md` は封印対象で、編集すると pre-commit が止める。
`.githooks/pre-push` は「解除は端末から人間が合言葉を打つ形にする。
**非対話セッション（AIの実行環境）では `/dev/tty` が開けず、そこで確実に止まる**」と
明記しており、`AUDIT_CHARTER.md` §6-5 が理由を述べている ——
**AIが自分の制約文書を書き換えた**のが、この仕組みを作った事故そのものである。
依頼者の許可があっても機械は止まる。設計どおりであり、突破しない。

**【追記】依頼者が `.tmp/domain-glossary.patch` を適用し、再封印した。**
差分がパッチと完全に一致すること、`MANIFEST` の変更が `domain.md` の1行だけであること、
14件の照合が全て一致することを確認したうえで取り込んだ。
**正典と橋の両方に表がある状態になった。**

封印の外側にも置いてある ——  `docs/product/legacy-terms.md` に対応表を作り、
`README.md` と `.claude/commands/decisions.md` から導線を張った。
正典を書き換えなくても、コードで `森` に出会った相手は表へ辿り着ける。
`domain.md` へ1行のポインタを入れるなら `.tmp/domain-glossary.patch` を適用して
再封印する（人間の操作）。**それが無くても機能する形にしてある。**

  森=アプローチ可能圏/構成コミュニティ  林=接点継続中  木=応募  幹=合格
  「種」は比喩ではない（すべて「種類」等の誤検出だった）

`basic/DESIGN.md:1017` に `npx @google/design.md lint` を叩けという指示があった。
**存在しないツールである**（雛形からの持ち込み）。`basic/` は変更しない領域だが、
AIはこれを守るべき指示として読むため、依頼者の許可を得て無効化した。

### 7. 作った道具が、着手導線から見つからなかった

本日 `decisions:show` / `decisions:missing` と S9〜S12 を足したが、
**`README.md` にも `HANDOFF.md` にも `.claude/commands/` にも書かれていなかった。**
次のAIは道具の存在を知らないまま 49万字を開こうとする。作っただけでは体制にならない。

導線を通した ―― README に「`db/DECISIONS.md` は開かない」節、
`.claude/commands/decisions.md`、`app/_styles/` の説明。
`HANDOFF.md` は `02aa6bd` 時点のまま全面的に古かったので実測で書き直した
（自ら「いまの状態だけを持つ」と宣言している文書である）。

その過程で自己参照がまた別の扉から入った。**書いた例文の番号が、
欠番の参照元として数えられた。** 例には実在する番号だけを使い、
**欠番の一覧は生成物（索引）1箇所にだけ置く**ことにした。他の文書はコマンドを指す。

   `pnpm decisions:missing` で下ごしらえが出る。
