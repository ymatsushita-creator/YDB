`.consultant/CHARTER.md` §4 の標準工程「計画 → 狭い実装 → 検証 → 独立レビュー」の
最初の段を踏む。**この段では実装しない。**

## 1. 観察（`investigator` サブエージェントに渡す）

- `db/DECISIONS-INDEX.md` を引き、**同じ論点が過去に決着していないか**を最初に見る。
  決着していれば覆す提案ではなく、その決定を持ち帰る
- 触る場所（`src/commands/` 書き込み・`src/queries/` 読み取り）と影響範囲を列挙する
- 守っているテスト（`tests/NN_*.test.ts`）を挙げる

## 2. 診断

外部ツールで現状の構成所見を取る（在ることの確認。これだけを根拠にしない）:

```
$(cat .consultant/TOOL_PATH) analyze --repo .
```

雛形プロンプトが要るなら:

```
$(cat .consultant/TOOL_PATH) prompt --repo . "<目的>"
```

## 3. 計画として出す

- **変更理由** —— どの仕事のどの詰まりを解くのか（ページやDB構造ではなく仕事単位で）
- **禁止範囲** —— 触らない場所（`basic/` / 適用済みマイグレーション / `.audit/` / 生成物）
- **完了条件** —— `pnpm verify` に加えて、画面またはSQLで何を確かめるか
- **テスト条件** —— 先に落ちるテストを書く。何を確かめないかも書く

## 進んではならない場合

- 監査が **Critical / High** を出している（`kurosaki audit --repo .`）
- 監督官の承認が無い（`SUPERVISOR.md`）

どちらも、計画を出すところまでで止める。
