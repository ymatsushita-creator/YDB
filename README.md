# YouthDB

起業家アカデミーの集客から選考までを一元管理するデータベースと、その上のダッシュボード。

森 → 林 → 木 → 幹 という段の考え方で、集客の広がりと選考の進み方を同じ場所で見る。

| 段 | 実体 | 単位 |
|---|---|---|
| 森 `partner_reaches` | 個人を識別しないリーチ | 接触機会（推定値） |
| 林 `identified_person` | 識別済みで、直近に接点がある人 | 人 |
| 木 `applicant` | その年度に応募した | 応募 |
| 幹 `accepted` | 最終選考を通過した | 応募 |

森だけ単位が違うのでファネルには並べない。林（人）と木・幹（応募）も
単位が違うため、同じ折れ線には載せず段として並べている。

## 動かす

```bash
pnpm install
```

```bash
pnpm db:reset && pnpm dev
```

`pnpm db:reset` は `.pgdata/` を作り直し、参照データ（本番用＋サンプル）と
4年度分のデモデータを投入する。2027年度だけ進行中の年度として作られ、
滞留・担当未割当・保留が画面に現れる。

デモデータは**同じ日に流せば**同じになる。乱数のシードは固定だが、
生成の打ち切り日（「今日」）が実行日に依存するため、日をまたぐと
行数が変わり、以降の乱数系列もずれる。日付を固定したいときは
`seedDemo(db, { asOf: '2026-08-06' })` を使う。

**開発サーバを起動したまま `db:reset` を実行しないこと。** サーバが
削除前のデータファイルを掴んだままになり、画面が古い数字を出し続ける。
先に `db:reset`、そのあと `pnpm dev`。

```bash
pnpm test
```

```bash
pnpm tokens
```

```

  DESIGN.md           デザイントークン（frontmatter が tokens.css の入力）
  academy_schema.sql
  academy_views_revised.sql

db/
  DECISIONS.md        原典から変えたところと、その理由。まずここを読む
  migrations/         スキーマとビュー。適用済みのファイルは編集しない
  seeds/
    0001_reference.sql          本番用。未確定のマスタは入れない
    0001_reference.example.sql  動作確認用のサンプル。本番では読まない

src/
  db/                 ドライバの薄い抽象とマイグレーションランナー
  queries/            ダッシュボードの問い合わせ。SQL はここに集める
  seed/               デモデータ生成

app/                  Next.js App Router

```

## データベースについて

開発とテストは **PGlite**（WASM 版 PostgreSQL 18）で動く。デーモンを
必要としないため `pnpm test` だけで完結する。本番の想定は PostgreSQL 15 以上。

`src/db/client.ts` の `Db` インターフェイスは `query` / `exec` / `close` の
3つだけなので、node-postgres への差し替えは `src/db/server.ts` に閉じる。

### 触る前に知っておくこと

**日付は必ず `jst_date()` を通す。** `timestamptz::date` と `CURRENT_DATE` は
セッションのタイムゾーン依存で、UTC 接続だと日本時間の午前9時までが前日に寄る。
接続設定を変えただけで過去の集計値が動く。今日を取るときは `jst_today()`。

**状態遷移ログは追記のみ。** `status_histories` は UPDATE も DELETE も
トリガで拒否される。訂正は打ち消し行の追記で表現する。訂正を訂正すると
元の記録が復活する（会計の逆仕訳と同じ）。有効な遷移は
`v_effective_status_histories` が解決する。

**適用済みのマイグレーションは編集しない。** チェックサムが変わると
ランナーが止まる。定義を変えるときは新しい番号のファイルを足す。

**集計マスタは追加と非活性化で運用する。** `void_reasons` /
`withdraw_reasons` / `channels` の既存行は更新しない。`is_active = false`
にして新しい行を足す。過去の集計の意味が変わってしまうため。

これは裏を返すと、**最初に入れた値が事実上の初期値として固定化される**
ということでもある。だから本番の参照データ（`db/seeds/0001_reference.sql`）は
分類が確定するまで空にしてある。`channels` と `void_reasons` は0件、
`withdraw_reasons` は `unconfirmed`（未確認）の1件だけ。
動作確認用のサンプルは `*.example.sql` にあり、本番のシードでは読まれない。

**辞退には必ず理由が要る。** 理由が分からないときは `unconfirmed`（未確認）を
選ぶ。NULL を許すと「まだ聞けていない」と「本当に理由がない」が
集計上区別できなくなる。

## 経緯

原典（`basic/`）はテーブルとビューの定義だけがあり、実際に動かした形跡が
なかった。実行可能にして計測したところ、意味論は正しいが実用にならない点と、
定義どおりに動いていない点がいくつか見つかった。すべて `db/DECISIONS.md` に
理由付きで記録し、テストで固定してある。主なものだけ挙げる。

- 日付境界がセッションのタイムゾーン依存で、日次ファネルがずれていた
- `void_reasons.counts_as_application` が実装のどこからも読まれていなかった
- 訂正チェーンに循環を作ると、記録が静かに集計から消えた
- 集計の計算量が実用に耐えず、主画面が出るまでに数十秒かかっていた
- 修正（`counts_as_application` の尊重）が別のビューを壊し、
  同じ人が同じ年度に2つの段で現れていた
