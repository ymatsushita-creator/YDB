# YouthDB

起業家アカデミーの集客から選考までを一元管理するデータベースと、その上のダッシュボード。

森 → 林 → 木 → 幹 という段の考え方で、集客の広がりと選考の進み方を同じ場所で見る。

| 段 | 実体 | 単位 |
|---|---|---|
| 森 `partner_reaches` | 個人を識別しないリーチ | 接触機会（推定値） |
| 林 `identified_person` | 識別済みで、直近に接点がある人 | 人 |
| 木 `applicant` | その年度に応募した | 応募 |
| 幹 `accepted` | 最終選考を通過した | 応募 |

森だけ単位が違うのでファネルには並べない。森は(4)流入元（`/sources`）に置く。
林（人）と木・幹（応募）も単位が違うため、同じ折れ線には載せず段として並べている。

## 動かす

```bash
pnpm install
```

```bash
pnpm db:reset && pnpm dev
```

`pnpm db:reset` は `.pgdata/` を作り直し、参照データ（本番用＋サンプル）と
4年度分のデモデータを投入する。2027年度だけ進行中の年度として作られ、
滞留・担当未割当・保留が画面に現れる。

デモデータは**同じ日に流せば**同じになる。乱数のシードは固定だが、
生成の打ち切り日（「今日」）が実行日に依存するため、日をまたぐと
行数が変わり、以降の乱数系列もずれる。日付を固定したいときは
`seedDemo(db, { asOf: '2026-08-06' })` を使う。

**開発サーバを起動したまま `db:reset` を実行しないこと。** サーバが
削除前のデータファイルを掴んだままになり、画面が古い数字を出し続ける。
先に `db:reset`、そのあと `pnpm dev`。

```bash
pnpm test
```

289件。新しい判断にはテストが1つ以上ある。

```bash
pnpm tokens
```

`basic/DESIGN.md` の frontmatter から `app/tokens.css` を生成する。
**生成物なので手で編集しない。** 色を変えるときは `DESIGN.md` を直す。

### 公開して見せる（デモモード）

```
https://ydb-ten.vercel.app
```

`VERCEL` を検出すると（あるいは `YOUTHDB_DEMO=1`）、**永続を諦めて
起動のたびに使い捨ての DB を組み立てる**。サーバレスには書き込めるディスクが
無く、`.pgdata/` も git に入っていないため配られない。

**これは Pilot の本番ではない。** 判定は押せるがインスタンスが入れ替わると
消える。実データも認証も無い。だから画面の右上に
「デモ ・ 架空データ ・ 保存されません」と赤字で出している。
URL を渡された人には、それが実データかどうかを確かめる手段が無いため。

Pilot に必要なもの（バックアップ・認証・DB の分離ほか7点）は
`docs/pilot/DEPLOY-READINESS.md` にあり、**どれも満たしていない**。

### 実データを置く場所を間違えない

`db/seeds/` は **git の追跡下**にあり、GitHub の2リモートへ push される。
**リポジトリは public である。** 候補者や職員の氏名・メールを置くと、
そのまま公開される。

実データの置き場所は `db/private/` だけ（`.gitignore` 済み）。
受け取り方と手順は `docs/pilot/DATA-INTAKE.md`。

### 実年度と創作のデモは同居できない

`src/seed/demo.ts` は 2024〜2027 の4年度を**創作している**。
実在する 2026年度と重なるため、同じ DB に入れると `enrollment_year` の
UNIQUE で衝突する。衝突を避ければ**創作の応募が実在の年度にぶら下がる**ので、
そちらのほうが悪い。

```
pnpm db:reset   サンプル＋デモ。実年度は入らない
seed(db)        本番。実年度が入る。デモは入らない
```

判定は `src/db/migrate.ts` の `loadSeeds`。理由は `db/DECISIONS.md` C-28。

## データベースについて

開発とテストは **PGlite**（WASM 版 PostgreSQL 18）で動く。デーモンを
必要としないため `pnpm test` だけで完結する。本番の想定は PostgreSQL 15 以上。

`src/db/client.ts` の `Db` インターフェイスは `query` / `exec` / `close` の
3つだけなので、node-postgres への差し替えは `src/db/server.ts` に閉じる。

### 触る前に知っておくこと

**日付は必ず `jst_date()` を通す。** `timestamptz::date` と `CURRENT_DATE` は
セッションのタイムゾーン依存で、UTC 接続だと日本時間の午前9時までが前日に寄る。
接続設定を変えただけで過去の集計値が動く。今日を取るときは `jst_today()`。

**状態遷移ログは追記のみ。** `status_histories` は UPDATE も DELETE も
トリガで拒否される。訂正は打ち消し行の追記で表現する。訂正を訂正すると
元の記録が復活する（会計の逆仕訳と同じ）。有効な遷移は
`v_effective_status_histories` が解決する。

**適用済みのマイグレーションは編集しない。** チェックサムが変わると
ランナーが止まる。定義を変えるときは新しい番号のファイルを足す。

**集計マスタは追加と非活性化で運用する。** `void_reasons` /
`withdraw_reasons` / `channels` の既存行は更新しない。`is_active = false`
にして新しい行を足す。過去の集計の意味が変わってしまうため。

これは裏を返すと、**最初に入れた値が事実上の初期値として固定化される**
ということでもある。だから本番の参照データは、分類が確定したものしか入れない。

| マスタ | 本番 | なぜ |
|---|---:|---|
| `withdraw_reasons` | 1件 | `unconfirmed`（未確認）だけ。無いと辞退そのものを記録できない |
| `channels` | **0件** | 6分類の案はあるが**まだ運用が始まっていない**。確定ではない（D-14） |
| `void_reasons` | **0件** | `counts_as_application` が集計定義そのもの。運用に照らしてから |
| `seasons` | 1件 | 2026年度。**4つの日付のうち1つは推測値**（D-8） |
| `selection_steps` | 4件 | 応募受付 → 書類選考 → グループ面接 → 最終面接 |
| `evaluation_criteria` | 6件 | 最終面接の6軸（各4点満点）。**書類選考の軸は呼び名が未確定で入れていない** |

**`channels` が0件だと接点を1行も記録できない**（`touchpoints.channel_id` は NOT NULL）。
選考の1周は回るが、**森と流入元は実データを入れても全部0のままになる**（C-31）。

動作確認用のサンプルは `*.example.sql` にあり、本番のシードでは読まれない。

**辞退には必ず理由が要る。** 理由が分からないときは `unconfirmed`（未確認）を
選ぶ。NULL を許すと「まだ聞けていない」と「本当に理由がない」が
集計上区別できなくなる。

## デザイン

**NEO ACADEMIA ブランド**に従う。最重要原則は **「色は線、面は黒」**。

ネオン4色（イエロー `#F0F000` / ピンク `#F03090` / シアン `#00C0F0` /
グリーン `#50F000`）は**線と短いラベルにだけ**使う。
**面を塗ってよいのは黒だけ。** 白と黒で構造を作り、その上に色を線として走らせる。

この原則はトークンの側で強制してある ―― 面に使われるトークン
（`primary` / `brand-navy` / `card-tint-*`）はすべて白か黒に倒してあるので、
**アクセント色の面塗りが構造的に作れない**。

- ブランド名は**必ずロゴ画像で出す**（`public/brand/`）。極太テキストで
  「NEO ACADEMIA」と書くとロゴと競合する。比 3.15:1 を崩さない
- **色・字送り・角丸を直値で書かない。** `var(--color-*)` を使う
- `app/tokens.css` は生成物。直すのは `basic/DESIGN.md` のほう

★印の6色だけは規定に無い。ネオン色は白背景の文字として読めないため、
色相を保ったまま暗くした派生である（`DESIGN.md` の中で区別してある）。
理由は `db/DECISIONS.md` C-29。

## 経緯

原典（`basic/`）はテーブルとビューの定義だけがあり、実際に動かした形跡が
なかった。実行可能にして計測したところ、意味論は正しいが実用にならない点と、
定義どおりに動いていない点がいくつか見つかった。すべて `db/DECISIONS.md` に
理由付きで記録し、テストで固定してある。主なものだけ挙げる。

- 日付境界がセッションのタイムゾーン依存で、日次ファネルがずれていた
- `void_reasons.counts_as_application` が実装のどこからも読まれていなかった
- 訂正チェーンに循環を作ると、記録が静かに集計から消えた
- 集計の計算量が実用に耐えず、主画面が出るまでに数十秒かかっていた
- 修正（`counts_as_application` の尊重）が別のビューを壊し、
  同じ人が同じ年度に2つの段で現れていた
- 絞り込みを効かせると集計が **9000倍**遅くなった。全件では速かったので
  片側だけ測っていたら見逃していた（A-16）
- 「やること」を4枝の `UNION ALL` で書き、除外条件の書き忘れで二重計上した。
  1本の `CASE` に組み替えて **1評価=1行を構造にした**（A-18 / C-23）

## いまどこにいるか

**MVP は完成し、採用の1周が画面の中で閉じている。** しかし
**実運用データでは1周していない。誰も運営として使っていない。**

```
今日やることを見る → 候補者を開く → 担当を決める / 替える / 保留を解く →
評価する（軸ごとに点と根拠）→ 確定する → 判定する → 次のステップへ
```

現在は **HOLD**。ブロッカーはソフトウェアの品質ではなく、**運用上の証拠が無いこと**。
「次に何をするか」の答えは機能ではなく**観測**である。

判定の全文と Go の条件は `docs/pilot/DECISION-LOG.md`（追記専用）、
引き継ぎは `HANDOFF.md`。

## 画面の言葉について

読み手は**面接官**である。DB の状態名や関数名を画面に出さない（C-32）。

- `pending` / `held` と書かない ―― 「まだ確定していない」「保留にしている」
- 集計の内部語を注記に使わない ―― 「窓の内側」ではなく「直近に接点あり」
- `domain.md` に無い語を画面が作らない ―― 「停止理由」ではなく「保留の理由」

**ただし、食い違いを勝手にどちらかへ寄せない。**
Community を「林」と訳していないのはそのためである ――
実装の林は**人**、Community は**組織**で、訳すと同じ語が2つの意味を持つ（D-11）。
画面では「連携先」と書いてある。旧語でも新語でもない第3の語だが、
どちらかに寄せるほうが危ない。
